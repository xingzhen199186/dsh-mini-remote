# 发版清单

一条命令一条命令地走。**第 4 步之前随便改，第 5 步之后不可撤销。**

版本号遵循语义化版本：功能新增走次版本号，只修 bug 走修订号（`package.json` 里现在是 `0.2.5`）。

---

## 1. 改版本号

改 `package.json` 的 `version`。

**没有第二处要改。** 2026-10-17 之前 `test/structure-deps.test.mjs` 里还钉着一份字面量版本，那属于"靠记性同步"的哑点，已经改成"必须等于 CHANGELOG 最顶上那条"。

## 2. 写日志

在 `CHANGELOG.md` 的 `## [0.1.x]` 之上加一节：

```markdown
## [0.3.0] - 2026-10-17

这一版的一句话概括（说人话，别写"优化了若干细节"）。

### 新加的
- 一条一件事，带一句"为什么值得加"。

### 修了的
- 一条一个根因，不要写成"修了一些问题"。
```

**判据**：CHANGELOG 最顶上那条的版本号，和 `package.json` 的 `version` 一模一样。

## 3. 跑两遍验证

```bash
npm test                      # 离线测试
node client/verify.mjs        # 客户端那半边
```

**判据**：两条都是 0 失败。数字只许涨、不许掉——掉了一定是删了断言，别放过。

## 4. 看一眼要发出去的东西

```bash
npm pack --dry-run
```

**判据**：`unpackedSize` 在 2.3 MB 上下（2026-10-18 发 0.2.2 实测 2.3 MB、44 个文件），文件数 44 上下。明显变大就说明有不该进包的文件混进 `lib/` 了——`lib/art/.npmignore` 里那条 `out-*` 是唯一一道闸。

顺便扫一眼文件清单里有没有本机路径、密钥、`scratch/` 之类的东西。

## 5. 打标签并推送 ⚠️ **必须有，别跳**

```bash
git add -A
git commit -m "0.3.0：<一句话>"
git tag v0.3.0
git push origin main --tags
```

**这一步不是可选的。** 2026-10-18 发 `0.2.2` 时就漏了：`npm publish` 跑完了、tag 却没打，
只能回头补。**npm 上有版本、仓库里没 tag，"发布"其实是半拉子**——GitHub Release 必须挂在
tag 上，没有 tag 就没有 Release；别人翻仓库也找不到"这一版对应哪份代码"。

**判据（三条都要对）**：

- `git tag --list` 里出现 `v0.3.0`；
- `git rev-parse v0.3.0` 和 `git rev-parse origin/main` **指向同一个 commit**
  （打了但指向旧提交，一样是错）；
- 远端也有：`git ls-remote --tags origin | grep v0.3.0` 能查到。

## 6. 发布

```bash
npm publish
```

**判据**：`npm view dsh-mini-remote version` 回的就是刚发的那一版；npm 页面上 README 的图能正常显示（图走的是 `raw.githubusercontent.com` 绝对地址，不依赖包内文件）。

## 7. 事后核对

- GitHub 的 Actions 页面上，这次 tag 的 `gate` 是绿勾。红了的话，发出去的那一版就是带着红的那一版——**先修，再发修订号**。
- 换一台没装过的机器（或清掉本地 `node_modules`）按 README 装一次，确认装得上、手机能连。

---

## 为什么这些步骤值得写下来

`v0.2.0` 发在 2026-10-08，之后仓库又积累了 41 个提交却没有再发一版——不是因为不敢发，是因为**没有一条固定的路径**，每次都要重新想一遍"我是不是漏了什么"。

CI 管住的是"代码没坏"，这份清单管住的是"发出去的东西对"。两件事不能互相替代。

---

## 两条硬规矩

- **`npm publish` 和 `git tag` 推送，由你自己执行——但两样都要做。** 「由你执行」说的是
  **谁写的代码谁不发布**（发布这一步要有第二双眼睛，哪怕那双眼是十分钟后的你）；
  不是"做一件就够"。第 5 步和第 6 步是**两个动作**，缺一个就不是完整的一次发版。
- **版本号由你定。** 改之前先想清楚这次是"功能新增"还是"只修 bug"，别顺手改成习惯的下一个号。
