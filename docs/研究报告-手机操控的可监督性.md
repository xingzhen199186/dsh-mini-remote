# 研究报告：把「AI 操作手机」做成可监督的事

> 研究日期 2026-11-10。对象：社区项目 DSH Go（<https://github.com/ccch1mneyyy/dsh-Go>，本地 `I:\DSH\dsh go\dsh-Go-main`）。
> 材料：仓库 README、`docs/guide/zh/` 下 12 篇用户指南中的对话、手机操控、设置、插件、分享几篇。
> 本文只做**理解与差距分析**，不含执行方案；执行方案另由顾问给出。

---

## 一、两条路线的差别，决定了什么能抄、什么抄不了

| | DSH Go | 我们（极简遥控器） |
| --- | --- | --- |
| 引擎在哪 | **手机里**（内置 Ubuntu + Node，PRoot，免 root） | **电脑上** |
| 手机端角色 | 既是界面，也是执行体 | 界面 + 被操作的对象 |
| 手机操控由谁发起 | 手机上那个引擎 | 电脑上的会话，经手机桥下发 |
| 断网时 | 本机引擎仍可跑（模型仍需联网） | 基本瘫痪 |

**关键推论**：他们的手机操控是「本地、可当场监督」的形态——引擎、界面、被操作对象在同一个系统里，所以能弹确认卡、能画浮层、能随时掐断。我们的操控是「远端下发」，监督必须**跨一条网络**完成，这是所有设计的前提。

---

## 二、明确抄不了的（不要在这上面花时间）

| 能力 | 为什么抄不了 |
| --- | --- |
| 内置 Linux 运行时、本机跑 DSH | 与产品定位冲突：我们就是让电脑干活、手机当遥控器 |
| SSH / DSH Remote 连接 | 我们已有内网 / Tailscale / 隧道三条线路，覆盖同样的场景 |
| 插件原生 UI SDK（工具卡、表单、面板） | 我们是网页插件，UI 由插件自己渲染；两套体系 |
| DS Bot、对话日志导出 | 与本产品无关 |
| 中英双语 | 用户明确只要中文 |

## 三、我们的现状（可复用的底座）

已经有的、可以被新设计直接用的东西：

1. **无障碍服务**：`observe`（控件 + 可见文字）、`tapIndex`、`back`、`swipe`、`input`、`shotBase64`；
2. **手机桥**：长轮询 + 结果回投 + 一次性投递 + 在线窗口；
3. **前台服务 + 部分唤醒锁**：锁屏后桥仍存活（已真机验证）；
4. **通知通道**：可发通知、可带跳转；
5. **App 内注入层**：设置页的板块、折叠行、返回手势都是注入实现的，只在 App 生效；
6. **失败透传**：手机原话会带回给模型。

已经拍板**不做**的（有恢复条件，记在 `docs/P2-手机桥.md`）：

- 签名验签、逐次授权、硬性拦截（`ALLOW_ALL_SCREENS = true`，所有界面都读、都点）；
- 按坐标点击；通知内直接回复。

**这条很关键**：下面所有建议都必须在「不设硬拦截」的前提下成立，否则就是在推翻既有决策。

## 四、差距清单（按用途分组）

### A. 保护：不改变能力，只减少泄露

**A1 敏感信息打码（我们认为最该做的一条）**

- 现状：`observe` 把屏幕上的可见文字**整段**交给模型，没有筛选。
- 风险：银行、证件、验证码页面上出现的号码会进入对话与模型请求；一旦用户截图或分享，等于二次扩散。
- 他们怎么做：银行卡号、身份证号在发给模型前先打码。
- 我们适配后的形态：在手机侧（`observe` 出结果之前）做**规则打码**——长数字串、疑似卡号/证件号按固定位数保留首尾。**不增加任何拒绝**，只是把数字遮掉。
- 冲突点：无。它不拦操作。
- 成本：小（手机端一个纯函数 + 单测）。

**A2 三档确认（2026-11-10 决定要做）**

- 三档：**始终免确认**（默认，等于我们现在的样子）/ **本任务免确认**（每轮问一次）/ **每次都问**。
- 关键认识：这不是"新增一套拦截"，而是**把同一能力做成档位**，默认档位与现状完全一致；另两档是用户需要更谨慎时自己往下拨的选择。**装上它，现有使用方式不变。**
- 因此它与「不设硬拦截」并不冲突——**不拦，只是问**；而且默认不问。
- 仍要付的代价是真实存在的：需要"动作挂起等回话"的状态、手机上的确认浮层、超时判定（他们定 30 秒不选=拒绝）。**成本在机制，不在行为。**
- 设计注意：确认卡必须有"无人值守时不要让任务假装成功"的语义——超时拒绝要如实回报，不能当成已执行。

---

### B. 可停：让用户在手机上掐得断

**B1 手机上没有任何停止入口（真实缺口）**

- 现状：任务在手机上跑起来后，用户只能回电脑停；手机端无入口。
- 他们怎么做：悬浮条（胶囊 / 卡片 / 小球），带暂停与停止；按住小球一秒直接停。
- 关键技术点：**无障碍服务可以画浮层（`TYPE_ACCESSIBILITY_OVERLAY`），不需要「显示在其他应用上层」权限**。这绕开了我们先前拒绝悬浮窗的理由。
- 我们适配后的形态：一个极小的可拖动胶囊，只放「停止」，点击即撤销本次任务授权并丢弃队列。不做卡片、不做暂停（暂停需要队列语义，成本大得多）。
- 冲突点：无（它是收回授权，不是拦截操作）。
- 成本：中（浮层生命周期、熄屏/锁屏的表现、与桥的状态同步）。

### C. 可查：不让它悄悄跑飞

**C1 没有超时**

- 现状：任务一旦开始，只要模型继续调用工具就会一直执行；电脑侧断了也没有自停机制。
- 他们怎么做：连续 3 分钟没有新操作，任务自动结束。
- 我们适配后的形态：**手机侧空闲计时**——单位时间内没有任何新指令到达，就自行解除武装并把「已自动停止」回报给电脑。
- 冲突点：无。
- 成本：小。

### D. 可解释：让用户知道刚才发生了什么

**D1 没有操作记录**

- 现状：每个动作的结果回给模型，但手机上不落任何可回看的记录。
- 他们怎么做：操作记录（含打码后的输入内容）。
- 我们适配后的形态：手机侧保留最近 N 条（时间、动作、目标标签），在设置页可查看。**只记标签不记内容**。
- 冲突点：无。
- 成本：小到中。

### E. 这次不建议做的（记下理由，免得反复讨论）

| 他们的 | 为什么我们现在不做 |
| --- | --- |
| ~~三档确认 + 确认卡~~ | **已改为要做**（2026-11-10 用户裁决，见下节 A2）。原先写成"冲突"是我判断错了：它的默认档位等于现状，不改变任何行为 |
| 应用名单（支付/银行不碰） | 同上；但可以作为**用户自定义名单**的形式稍后再议 |
| 解除限制三项 | 我们已经全部放开，等于始终处于「解除限制」状态 |
| 自动恢复无障碍（Shizuku/ADB） | 需要引入 Shizuku 或自连 ADB，对非技术用户门槛过高；与我们「降低门槛」的硬要求冲突 |
| Android Shell | 权限面过大，且与手机操控无关 |
| 主题色/图标/桌宠出屏/平板布局/i18n/分享链接回放 | 体验类，不影响可用性，先不动 |

## 五、三条必须写进设计前提的边界

1. **不能点亮屏幕、不能解锁**。已实测：全屏通知在这台荣耀上不生效；有效的是系统「通知亮屏提示」+ 用户自己解锁。任何「自动执行」的方案都必须承认这一点。
2. **国产 ROM 的后台限制不在标准权限里**。后台弹出、自启动、电池优化三项各自独立，且随版本变化。
3. **无障碍浮层 ≠ 悬浮窗**。前者由无障碍服务绘制，不需要额外权限；后者要用户去系统里授权，观感也更容易被当成流氓软件。设计上应优先前者。

## 六、给设计者的输入（我们希望的产物）

请基于以上，产出一份**执行方案**，要求：

1. 按阶段拆分，每阶段**独立可用**，不要一次性大改；
2. 每阶段写明**验收标准**——必须是可以当场判断的现象（"能看到什么/读数是几"），不要"运行正常"这类无法判定的说法；
3. 标明每阶段的风险与**回滚方式**；
4. 明确指出哪些点**必须用户拍板**，哪些可以按工程判断直接做；
5. 不许引入新的硬性拦截（会推翻既有决策），也不许新增需要用户跑命令才能安装的依赖（会推翻"降低门槛"的硬要求）。
