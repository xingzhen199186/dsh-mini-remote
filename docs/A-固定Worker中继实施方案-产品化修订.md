# A：固定 Worker 中继实施方案（产品化修订）

> 状态：产品化设计评审稿，2026-10-27。只规划，不表示 A 已开发、部署或收费。
>
> 前置文档：`docs/A-固定Worker中继实施方案.md`。本稿不替代其中的协议细节和测试清单，而是把它改成一条可运营、可停止、可扩量的实施路线。
>
> 证据口径：**[仓库证据]** 指本仓库代码或文档；**[远端源码证据]** 指 `ref-a/` 中已下载的参考项目远端文件；**[工程推断]** 指本项目设计，尚需实现和验证；**[估算]** 指容量、工期或成本假设，不是实测或报价。

## 0. 修订结论

### 0.1 直接结论

**A 值得做“邀请制产品化内测”，但现在不应直接全量产品化，更不应公开注册。**

它要交付的不是一段 Worker 反代代码，而是一项持续服务：用户不准备 Cloudflare 账号、域名或服务器，打开开关后即可扫码；我方负责固定入口、准入、限额、撤销、故障处置、隐私说明和客服。插件公开下载不等于中继可以匿名无限注册。

近期只做 A 的 quick 路径，并把 quick 生命周期、运营开关和回退先补齐。命名隧道 lease（B）、Durable Object bridge、多区域、账号计费、可视化后台都不是首发依赖。

进入更大范围 Free 或 Paid 前，必须同时满足：

1. 转发正确：HTTP、SSE、WebSocket、文件流和 Host/Origin 全部通过真机验收；
2. 服务可控：邀请准入、单 id 撤销、关闭新注册、全局停用均演练成功；
3. 风险可兜底：target 白名单、限流、日志脱敏、公网管理路由拒绝测试通过；
4. 体验可恢复：Worker 故障不会拖垮 quick，电脑端能给出裸 quick、C 或自建 frp 的明确替代；
5. 运营可持续：真实请求、CPU、长连接、客服量和成本有至少两周数据，且条款与隐私审查没有阻断项。

任何一项不满足，都停在当前阶段；不能用“先公开再补运营”换进度。

### 0.2 相比现有方案改了什么

| 修订点 | 现有方案基础 | 产品化修订 | 时间 |
|---|---|---|---|
| 上线单元 | 原型 → 内测 → Free 限量 → Paid | 增加运营准入、客服、审计和停止条件；每个 Phase 都有交付物、依赖、验收和回滚 | 近期 |
| 首发规模 | Free 中度活跃实例软上限 100 | **100 只是容量软线，不是首发目标**；先 5–10 个邀请实例，再视门槛扩到不超过 25 个 | 近期 |
| 注册方式 | 插件持 id/secret 自服务注册 | 新身份先经服务端准入；邀请码只用于首次开通，后续只凭本实例 id/secret 心跳，不把邀请码塞进二维码 | 近期 |
| 身份生命周期 | D1 管身份，KV 管 target | 明确 unregister 只停用 target，不释放 id；管理撤销保留墓碑，避免旧固定地址被他人重新认领 | 近期 |
| 插件前置 | quick 尚未统一接入监督器 | 把 quick 接入 TunnelSupervisor、固定 Host 参数和 RelayProvider 状态机列为 Phase 0 阻断项 | 近期 |
| 运营后台 | 原则性运维要求 | 近期就是 Cloudflare Access 保护的 admin API + CLI，包含列表、用量、撤销、关注册、全局停用和审计 | 近期 |
| Free→Paid 触发 | Free 60k/日软线，另有 700 万/月预测线 | Free 用与自身容量一致的触发：60k/日或月度等效预测 210 万请求提前评审；700 万是 Paid 软线，不是 Free 升级前置 | 近期/远期 |
| 容量模型 | 我方 442 请求/实例/日 | 增加参考项目“启动/变化才注册”的 252 请求模型；二者在线语义不同，不能只选看起来更便宜的一种 | 近期 |
| 技术演进 | A、B、bridge 已有源码参照 | 借 A 的窄代理和失败回退；不默认引入 B 的账户资源代建，也不默认引入 DO bridge | 远期按门槛 |
| 产品承诺 | 固定 Origin、非 E2EE | 补充“无自动跨 Origin 故障转移”“Free 无 SLA”“不承诺国内可达或永久免费” | 持续 |

### 0.3 近期必须做与远期才做

**近期必须做：**quick 统一生命周期；id/secret 与服务端准入；D1 身份、KV target、短 Cache；窄 target 白名单；HTTP/SSE/WS/文件流；撤销和全局停用；最小 admin API/CLI；监控、日志脱敏、邀请制、客服与回滚演练。

**远期才做：**Paid 扩量和超额预算、按 id 产品配额、账单、可视化运营后台、完整滥用治理、密钥轮换自助化、公开状态页与 SLA、自助导出/删除、多区域，以及有数据支持的 B 或 bridge 评估。

**明确不做：**不替换 C、自建 frp、局域网、Tailscale；不做自动跨境或跨 Origin 切换；不把 A 宣传成 E2EE；不把参考项目的存在当作价格、稳定性或合规证明。

## 1. 参考项目再核对

### 1.1 三条真实路径

#### 路径 A：quick 注册表 + Worker 反代

**[远端源码证据]**

- `ref-a/relay.js:108-181` 提供 register/unregister；身份和 target 存在 D1。unregister 直接删除 registration，与我方拟保留身份所有权不同。
- `ref-a/relay.js:310-365` 的代理路径按 Host 找 id，每个数据请求读取 `relay_registrations`，再向临时 quick Origin 发起请求；请求体通过 body 流传递，重定向为 manual。
- `ref-a/wrangler.jsonc:24-27` 配置了 DO binding，因此 `ref-a/relay.js:253-260,328-334` 还会读取 lease mode 来决定 quick/bridge。也就是说，在这份部署配置下不能简单概括为“所有请求永远只有一次 D1 读”。
- `ref-a/0007_relay_registry.sql` 定义 `relay_registrations` 和固定窗口限流表；`ref-a/relay.js:33-37,95-159` 是 30 次/IP/分钟、6 次/id/分钟的注册限流。
- `ref-a/relay.js:76-85` 只接受 HTTPS、根路径、无 query、无 userinfo 且主机名带 `.trycloudflare.com` 后缀的 target。这里是后缀判断，不等于我方更严格的“单标签、无显式端口、无 hash”规则，不能直接照抄成安全边界。
- `ref-a/relay.js:183-190` 与 `ref-a/wrangler.jsonc:54-57` 每 30 分钟清理一次；注册 90 天未见才 GC。90 天是记录回收周期，不是 45 分钟在线 TTL。
- `ref-a/relay.js:193-241` 有无 target 的 503 离线页，并对符合窄规则的带 hash `/assets/**` 成功响应添加一年 immutable Cache-Control；这不是 Cache API 业务响应缓存。
- `ref-a/relay.js:345-365` 处理 Host、部分转发头和 WebSocket Upgrade。源码存在不等于 SSE/WS 已经有生产压测报告。

参考客户端在本项目前稿已有逐行证据：它主要在 tunnel start、target 变化和失败重试时登记，**没有 15 分钟周期心跳**。这正是第 8 节第二个容量模型的来源。

#### 路径 B：服务方代建命名隧道 lease

**[远端源码证据]**

- `ref-a/relay-control.js:243-260,305-405` 的 claim 会通过 Cloudflare API 找到或创建命名隧道，写 ingress，找到或创建 proxied CNAME，再把该实例 tunnel token 返回给插件。
- `ref-a/relay-control.js:423-472` 区分 release 与 retire：release 只把 lease 标为 released，保留隧道和 DNS；retire 才删除 DNS、Tunnel 和 lease。
- `ref-a/0009_relay_leases.sql` 保存 tunnel、hostname、origin port、状态和 last_seen；`ref-a/0010_relay_lease_mode.sql` 增加 mode。
- `ref-a/relay-control.js:97-100` 的默认逻辑仍是 quick，环境或 lease mode 才切到 named/bridge。

这条路径要我方持有账户级 API 权限、管理每个用户的 Cloudflare 资源并处理 token、回收和孤儿资源。它不是 A 的免费延伸，也不是 C 的“用户自己配命名隧道”。

#### 第三条：Durable Object bridge

**[远端源码证据]**

- `ref-a/relay-bridge.js:145-210` 每个 id 对应一个 DO，保存一条插件 connector socket，新连接可替换旧连接。
- `ref-a/relay-bridge.js:222-348` 将 HTTP body、响应和下游 WebSocket 按 stream id 多路复用；`ref-a/relay-bridge-connector.ts` 是插件侧连接器和帧协议实现。
- `ref-a/relay.js:328-334` 在 bridge 无 connector 时可回退 quick；lease mode 是切换开关。

这是一套新的传输协议和连接器，不只是“把 KV 换成 DO”。它增加帧协议、背压、重连、版本兼容、DO 成本和运维面。源码和测试能证明实现存在，不能证明它已经适合我们的生产流量。

### 1.2 它没有给我们的答案

- **没有面向运营作者的 relay 后台。**`ref-a/index.js:365-375` 暴露的是 register/unregister/claim/release/retire/bridge 等插件自服务路由，没有 `/admin` 路由；运营依赖 D1 和 Cloudflare 控制台。
- **账单未知。**`ref-a/wrangler.jsonc` 能证明 D1、DO、cron、通配路由和 observability 的配置，不能证明 Workers 套餐、实际请求量、DO 时长或月度账单。
- **生产 SLO 未知。**这些文件没有给出 quick 可用性、D1 热路径容量、KV 一致性、SSE/WS 长稳、国内可达性或客服成本数据。
- **合规与滥用结果未知。**有限流和 target 限制不等于已经解决公开服务治理。

### 1.3 我们借什么、不借什么

| 借设计思想，重新实现 | 不直接借 |
|---|---|
| 固定一层子域；id 公开、secret 只证明注册所有权 | 自服务匿名创建身份；unregister 就删除身份并允许重新认领 |
| target 只指 quick Origin；不跟随重定向；不开放公共 target 查询 | 仅靠后缀匹配的 target 校验；把参考限流值当成我们的容量结论 |
| 数据面只做窄反代，应用配对和设备鉴权留在插件 | 每请求直接依赖 D1 作为我们 Paid 规模的默认热路径 |
| 离线页、流式 body、WebSocket 分支、带 hash 静态资源缓存思路 | 为所有 HTML/API 加缓存；为了省请求而采用 90 天在线 TTL |
| 新 transport 失败时保留 quick 退路 | 首发同时实现 claim、命名隧道资源管理和 DO 帧协议 |
| quick 之外的演进可能性 | 把“参考项目有源码”当成生产 SLO、价格或条款背书 |

## 2. 产品边界

### 2.1 用户得到什么

**[工程推断]**目标用户流程：

```text
安装公开插件
  → 打开“公网访问 / 固定地址”开关并阅读中继告知
  → Free 邀请阶段：仅首次输入一次邀请码
  → 插件自动准备 cloudflared、id/secret、登记与心跳
  → 固定地址端到端检查成功
  → 用户扫码或收藏固定地址
```

用户不需要 Cloudflare 账号、域名、控制台、服务器，也不应看见 tunnel token、D1、KV 或 DNS 配置。邀请码是内测准入手段，不是要求非技术用户理解另一套账号体系；后续是否变成账号/套餐权益，由商业化方案决定。

固定地址解决的是 **quick URL 改变时不必重新配对**。它不保证用户电脑永远在线，不保证 quick 可用，也不保证 Worker 故障时旧书签自动跳到另一个 Origin。

### 2.2 我方与插件分别负责什么

| 责任 | 我方运营服务 | 用户电脑上的插件 |
|---|---|---|
| 固定入口 | 域名、Worker、通配路由、身份命名空间 | 展示固定地址和状态，不伪造“已连接” |
| 身份 | 准入、secret 哈希、撤销、墓碑、审计 | 生成/保存 id/secret，损坏时明确提示，不静默换地址 |
| target | 白名单、45 分钟 TTL、短期缓存、停用 | quick URL 变化时登记，15 分钟心跳，停止时尽力注销 |
| 数据面 | 限流、窄反代、离线页、最小指标 | cloudflared 生命周期、本机服务、SSE/WS 协议本身 |
| 应用安全 | 不保存手机主 token，不绕过应用鉴权 | 配对、口令、设备会话和设备撤销仍按现有语义执行 |
| 故障 | 告警、关注册、单 id 撤销、全局停用、状态沟通 | 区分 tunnel 与 relay 故障；给裸 quick 等回退，不盲目重启隧道 |
| 用户关系 | 邀请、隐私政策、条款、客服、滥用处置、删除请求 | 提供可读错误和一键复制诊断信息，敏感值先脱敏 |

**secret 不是手机访问凭据。**它只能证明“谁有权更新这个 id 的 target”。撤销一部手机仍是插件设备名册的职责；撤销 relay id 是运营侧切断固定入口，两者不能互相替代。

### 2.3 与 C、frp、B 和其他路线的区别

| 路线 | 用户准备什么 | 固定地址 | 数据路径与主要责任 | 定位 |
|---|---|---|---|---|
| A：我方固定 Worker + 用户 quick | 基本不需要额外账号；内测需邀请资格 | 是 | 手机 → 我方 Worker → quick → 用户电脑；我方承担公共服务运营 | 非技术用户的低门槛选项 |
| C：用户自己的命名隧道 | Cloudflare 账号、域名、token、Public Hostname | 是 | 用户自己的 Cloudflare 配置；插件负责进程 | 已具备 Cloudflare 能力的用户 |
| 自建 frp | 自己的服务器、域名、证书和运维 | 是 | 自建服务器 → frpc；用户控制数据面 | 国内/自控路线，长期保留 |
| B：服务方代建 named lease | 用户少配置，但服务方管理 Cloudflare 资源 | 是 | 通常不经 Worker 逐请求反代；服务方管 Tunnel、DNS、token | 远期备选，不是 A 首发功能 |
| 裸 quick | 不需要账号 | 否 | Cloudflare quick → 用户电脑 | A 的即时回退之一 |
| LAN / Tailscale | 同网或 Tailscale 环境 | 视路线而定 | 不经过我方 Worker | 继续独立可用 |

**[仓库证据]**C 已按“先 C，后 A”完成（`docs/中继方案-C-A.md:87-100`）；自建 frp 已有插件侧实测，但现有 4 Mbps 服务器只适合单人邀请验证，不适合作为正式承载（`docs/国内中继方案框架.md:468-495,556-562`）。A 不能借上线之名削弱这些路线。

跨 A、C、frp、裸 quick 会改变 Origin，Cookie、书签和部分配对状态不能默认迁移。近期只做用户主动选择和清晰指引，不做自动切换。

### 2.4 明文与 E2EE 边界

```text
手机 HTTPS
  → 我方 Worker 终止第一段 TLS
  → quick 临时地址建立第二段 TLS
  → cloudflared
  → 127.0.0.1 上的插件
```

Worker 在两段 TLS 之间能处理明文 HTTP，因此理论上可见 URL、查询 token、Cookie、指令、回复和文件内容。Cloudflare 也在传输信任边界内。**A 不是端到端加密。**

近期开启页必须直白说明这一点，不使用“绝对安全”“零记录”“端到端加密”文案。降低信任成本靠最小日志、短保留期、可撤销和可删除，不靠隐瞒。

## 3. 近期总体设计：按 Paid 承载量写，按邀请制放量

以下为 **[工程推断]**，数值门槛属于 **[估算]**，需压测与控制台数据校准。

### 3.1 控制面与数据面

- 控制面：`relay.example.com/api/relay/v1/*`，负责准入、register、unregister、健康和管理。
- 数据面：`https://<id>.relay.example.com/*`，只使用一层子域，避免两层通配证书问题。
- 新身份先 `enroll`，已有身份才能 `register`。邀请关闭时，已有 active 实例仍可心跳；新 enroll 被拒绝。
- 数据面只从服务端存储取 target，拒绝请求参数中的 `url`、`target`、`X-Forwarded-Host` 指定上游，不支持 CONNECT。

最小 wire 契约：

| 接口 | 输入 | 成功与语义 |
|---|---|---|
| `POST /enroll` | id、secret、首次准入凭据 | 创建 active 身份并消费一次性邀请；返回 publicUrl，不返回 secret |
| `PUT /register` | id、secret、target | 验证身份，写入/续期 target；用于启动、URL 变化和心跳 |
| `POST /unregister` | id、secret | target 置 disabled；保留身份，204；失败不阻塞本地停用 |
| `GET /health` | 无参数 | 只报版本与基本存活，不暴露 id、target、数量或存储详情 |
| `<id>.../*` | 原路径、query、body、Upgrade | 解析有效 target 并代理；离线 503、撤销 410、上游错误 502 |

错误统一为机器可读 code、retryable 和必要的 Retry-After；不把 secret、target、D1/KV 错误或内部堆栈返回给插件/手机。

### 3.2 D1、KV、Cache API 的角色

**D1：低频控制面真相**

- `relay_identities`：id、secret 的 HMAC 哈希、状态、邀请来源、创建/撤销时间、last_seen；状态至少有 active/suspended/revoked。
- `relay_invites`：邀请哈希、状态、额度、过期时间、消费时间；不保存明文邀请码。
- `relay_admin_audit`：操作者、动作、id、原因、时间、requestId、前后状态；不记 secret、target、手机 token 或 query。
- 新身份与邀请消费必须在同一原子写入路径完成；已有 id 不允许被另一个 secret 重新认领。

**KV：高频读取的短期 target**

```text
target/v1/<id> → {
  version, state, targetOrigin, expiresAt, updatedAt
}
```

- state 为 active/disabled/revoked；targetOrigin 只允许已验证 quick Origin 或 null。
- target TTL 45 分钟；插件每 15 分钟带 ±20% 抖动续期。过期只让 target 失效，不删除 D1 身份。
- unregister 写 disabled；revoke 先更新 D1，再写 KV revoked。任一写入失败不能向管理端/插件报告完整成功，必须告警并进入重试或紧急处置。
- 不在每个手机请求中写 KV/D1，也不靠 KV“读—加一—写”实现精确全局计数。

**Cache API：节点内短加速，不是真相**

- 只缓存 target 记录，正向最多 5 秒、负向最多 1 秒；每次使用前仍检查 `expiresAt` 和 state。
- 不缓存 secret 哈希、邀请、管理响应或手机业务响应。
- KV/Cache 都有传播与节点差异。撤销目标为同节点 10 秒、跨节点 90 秒内生效并告警，但这是验收目标，不能在未实测前承诺“即时全局撤销”。高风险泄露且撤销传播无法验证时，直接加平台级 Host 阻断或全局停用，而不是等待 45 分钟 TTL。

KV 读取失败时返回不缓存的 503，不从不受信任的请求补 target，也不无限期服务陈旧记录。

### 3.3 id、secret、邀请与本地身份文件

- id 使用 16 字节 CSPRNG，编码成 26 字符小写 Base32 单标签；id 不复用 machine-id，也不是秘密。
- secret 使用 32 字节随机数，base64url 编码；服务端只保存带 server pepper 的 HMAC-SHA-256，pepper 放 Workers Secret。
- 本地身份写入 `$DSH_HOME/dsh-mini-remote/relay-identity.json`，原子替换；Unix 0600，Windows 依赖用户配置目录 ACL。身份文件不进入 settings.json、二维码、浏览器 payload 或日志。
- 文件损坏时显示“固定地址身份不可读”，由用户确认重置；不得后台悄悄生成新 id。重置后旧地址撤销、手机重新配对。
- Free 邀请是一次性、可过期、可限制次数的服务端凭据。插件公开后，任何客户端内置常量都不能当秘密；准入必须由服务端判定。
- MVP 不做无感 secret rotate。泄露时先撤销 id，再重置本地身份；否则“自动恢复”可能把旧手机带到攻击者 target。

### 3.4 target 与反 abuse 边界

注册时和每次代理前使用同一纯函数校验：

1. 仅 `https:`；无 userinfo、hash、query、非根路径和显式端口；
2. hostname 仅允许一个合法 quick 标签加 `.trycloudflare.com`，拒绝裸域、`api.`、多级子域、伪后缀、尾随点和 IP；
3. `redirect: manual`，绝不向上游 3xx 的第二地址继续 fetch；外部 Location 只交给浏览器导航；
4. 控制面 JSON 上限 4 KiB，限制方法和 Content-Type，不做泛化 CORS；
5. 注册、鉴权失败、数据面突发、Upgrade、请求体分别限制；管理接口与插件接口分离；
6. Worker 不能替代插件口令失败限流、本机路由门禁和设备撤销。

这套设计把能力限制为“已准入实例的 quick Origin 反向代理”，不是公共 HTTP 代理。

## 4. 近期计划（0～3 个月）

> 工作量均为 **[估算：人日]**，包含开发、测试和文档，不包含等待邀请用户、Cloudflare 故障或外部合规审查的墙钟时间。合计 **53～76 人日**。按 1 名熟悉项目的工程人员 + 约 0.2 人评审/运营投入，预期 10～12 周；若投入减半则顺延，不压缩验收。

### Phase 0：quick 生命周期前置统一（第 1～2 周，7～10 人日）

**目标**

让 quick 与 named 都经过可观察、可恢复的统一生命周期，再建立 RelayProvider 的独立状态机。不得在旧 quick 成功回调里塞一次 register 就算完成。

**仓库现状**

- `lib/tunnel.js:64-85` 的 quick 参数没有固定 Host 选项；A 需要可选 `originHostHeader`，只在 relay 开启时传给 cloudflared。
- `lib/tunnel-supervisor.js:25-32` 的 target 指纹不含 relay Host；新增字段必须进入指纹，否则开关变化可能不重建连接器。
- `lib/index.js:1374-1453` 只有 named 使用 TunnelSupervisor，quick 仍是独立三次启动循环。
- `lib/index.js:4935-4969` quick 状态仍来自旧变量，自动恢复产生的新 URL 容易漏给 relay。

**交付物**

1. quick 接入 TunnelSupervisor，复用 start/probe/retry/stop，不另造第二套 quick 重试状态机；
2. `originHostHeader` 进入启动参数和 target 指纹，named/C/frp 行为不变；
3. RelayProvider 接口及纯状态机：`attach(quickUrl)`、`detach({unregister})`、`snapshot()`，内部含 generation、超时、退避和心跳计时器；
4. 用注入 fetch/计时器的单测覆盖 A→B target、迟到响应、停止后在途请求、429 和 5xx；此阶段不接生产 Worker。

**依赖**

现有 TunnelSupervisor、quick/named 测试、C/frp 回归清单。RelayProvider 的生产 endpoint 此阶段不是依赖。

**验收标准**

- 模拟 20 次 quick 重启，每次新 URL 恰好触发一次 attach，旧 URL 的迟到结果不能覆盖新状态；
- detach 后定时器和在途响应均不能复活 provider；相同 URL 不重复登记；
- relay 关闭时 quick 的原有配对、重试、错误文案和退出行为不变；
- originHostHeader 改变会重建连接器，未开启 relay 时不添加该参数；
- 现有 quick、named、pairing、self-relay 测试全过，无第二套并行 quick 状态机。

**退出/回滚条件**

任一旧路线回归失败、URL 变化丢失或停止后仍有心跳，则不进入 Worker 开发。回滚是关闭尚未发布的 relay 分支或回退插件版本，不保留长期双实现。

### Phase 1：Worker 控制面与最小运营控制（第 3～4 周，12～16 人日）

**目标**

在隔离 staging 环境实现可准入、可注册、可撤销的身份/target 控制面；运营能力与管理鉴权同阶段交付，不等公开后再补。

**交付物**

1. D1 migration：identity、invite、admin audit；KV target；Cache API 短缓存；
2. enroll/register/unregister/health；id/secret 哈希、邀请消费、错误契约、5 秒控制面超时预算；
3. 严格 target 白名单、控制面体积极限、IP/id 注册限流；
4. 单 id suspend/revoke、关闭/恢复新注册、全局代理停用/恢复；所有写操作记审计；
5. Cloudflare Access 保护的 `/admin/relay/v1/*` 路由和同一 API 的 CLI；交互管理员用 Access 身份，CLI 用独立 service token，不用 URL 中的共享管理密码；
6. staging 的部署、回滚、secret 配置和 D1/KV 隔离说明。

**依赖**

Phase 0 契约；我方域名、Cloudflare 账号、Access 配置权限、测试 D1/KV。生产账单不是 staging 的前置，但套餐能力必须记录。

**验收标准**

- 新 id 无有效邀请不能创建；邀请只能消费一次；错误 secret 得 403；过期 target 或已 unregister 的身份也不能被他人认领；
- unregister 后不再代理，但原 secret 可恢复；revoke 后同 secret 也不能恢复，id 不重新发放；
- 所有恶意 target 用例都在任何上游 fetch 前被拒绝；嵌套后缀、端口、hash、尾点也覆盖；
- KV 写失败不返回注册成功；D1 撤销成功/KV 失败会告警并进入紧急流程，不显示“撤销完成”；
- 关闭新注册只挡新 enroll，已有 active 心跳和 unregister 仍可用；全局停用后数据面不代理，管理和 unregister 仍可用；
- 未通过 Access 的请求对所有 admin 路由均失败；CLI 每次写操作能在审计中对应到 actor、reason 和 requestId；
- 日志自动扫描不到 secret、邀请明文、手机 token、Cookie、Authorization、完整 target 或 query。

**退出/回滚条件**

Access 可绕过、身份可抢、撤销无审计、白名单可绕或运营开关不可用时，停止 Phase 2/3。staging 可删除通配路由并回滚 Worker；此时尚无生产用户，不允许把测试身份直接迁成正式用户来省事。

### Phase 2：数据面协议与安全验收（第 5～6 周，12～18 人日）

**目标**

只实现手机/B/远程窗口需要的窄反代，证明流式、长连接、Host/Origin 和错误语义正确。

**交付物**

1. 原路径/query 转发、方法与应用头处理、逐跳头清理、转发头重建、响应头保留；
2. HTTP/SSE/WebSocket 分支，请求体和响应体流式传递，不为计算长度而整包缓冲；
3. 普通响应头等待初始 15 秒，SSE/WS/慢文件不套统一 30/60 秒总时长；
4. 声明 Content-Length 超过 50 MiB 返回 413；chunked 用流式字节计数/中止或经验证的平台限制，不能只信声明；
5. 相对 Location 原样，同 quick Origin 的绝对 Location 改固定 Origin，外部 Location 不继续 fetch；
6. 503 离线、410 撤销、502 上游错误；页面 no-store/noindex/no-referrer，不含 target、secret 或内部信息；
7. 协议集成测试、恶意请求测试和真机测试报告。带 hash 静态资源一年缓存只在确有性能收益且命名核实后单独开启，不是本阶段放行条件。

**Host/Origin 规则**

- Worker 到 quick 的 Host 由目标 authority 决定；cloudflared 用 `originHostHeader` 让本机看到固定 relay Host；
- 浏览器 Origin/Referer 不改写成临时 quick Origin；无 Origin 不凭空添加；
- 删除客户端伪造的 Forwarded/X-Forwarded-*，由 Worker 重建必要的固定 Host 和 HTTPS 信息；
- 不把公网 Host 视为“本机可信”，不豁免 `/mini/api/*`、`/mini-remote/*` 的原有鉴权。

**依赖**

Phase 0 的固定 Host；Phase 1 的有效 target；可控测试源、隔离 Worker、真实 cloudflared、手机 4G/5G 与 Wi-Fi。

**验收标准**

- `/mini/api/state?a=1&a=2&q=%2F&x=a+b` 到上游逐项一致；Set-Cookie、状态和二进制响应不变，固定域 Cookie 带 Secure；
- SSE 首帧 2 秒内到，测试源逐块发送时第一块先于最后一块到客户端；连续 30 分钟无整段缓冲，断网 30 秒后重连与状态重放正确；
- WebSocket 101、文本/二进制、ping/pong、close 双向正常，远程窗口连续 30 分钟；设备撤销仍按插件语义生效；
- 50 MiB 上传/下载哈希一致，无整包内存增长；51 MiB 声明体得 413，chunked 超限也被中止；慢速传输不被固定总超时误杀；
- quick URL 改变后，固定书签在新 target 登记与探测完成后恢复，无需重新配对；
- 所有公网仅本机管理路由得到既定 401/403/404；3xx 到回环或外域不发生第二次 Worker fetch；
- 普通代理 CPU 目标 p95 < 5 ms，无持续超过 10 ms 的趋势；真实指标若不符，修正模型而非放行。

**退出/回滚条件**

SSE/WS 缓冲、管理路由暴露、任意上游、日志泄露或文件内存缓冲任一存在，均不得进入邀请测试。回滚到 Phase 1 的“仅控制面、无数据面路由”，插件继续使用裸 quick/C/frp。

### Phase 3：插件产品接入（第 7～8 周，10～14 人日）

**目标**

把已验收的 Worker 接进插件，完成用户可理解的开通、固定二维码、心跳、回退、撤销和配对。

**交付物**

1. 身份文件读写、一次性邀请开通、relay 开关和非 E2EE 告知；endpoint 随受控发布配置，不开放任意 secret 接收地址；
2. RelayProvider 生产接线：首次登记、target 变化、15 分钟心跳、固定地址健康检查、5 秒控制面超时、指数退避与 Retry-After；
3. 状态分离：`tunnel.url` 是诊断用临时 target，`relay.publicUrl` 是固定展示地址，二者健康状态分开；
4. pairing 新增固定 relay 类型，只有固定地址端到端健康时才标 active；relay 失败不等于 quick 进程失败；
5. 停止/切 named/停公网时尽力 unregister，卸载最多等 2 秒；普通 quick 重连不先注销身份；
6. 设置页和客服诊断文案：邀请无效、中继异常、隧道异常、需要重新扫码、身份重置。

**回退语义**

- 首次登记失败：quick 健康时给裸 quick 二维码，并说明地址是临时的；
- 曾 active 的短暂心跳失败：45 分钟 TTL 宽限内保留固定地址并标 degraded，不立即换源；
- 固定地址已不可用：电脑端提供裸 quick/C/frp 的新入口，说明换 Origin 需要重新扫码；旧固定书签不能由 Worker 自动迁移；
- Worker 故障不能触发 cloudflared 重启，也不能让局域网、Tailscale、C、frp 跟随停用。

**依赖**

Phase 0～2 全部通过；现有 pairing、设备名册、self-relay 和 C 的回归环境。

**验收标准**

- 安装后无需 Cloudflare 账号即可完成邀请开通；邀请只输入一次，secret/邀请不进入二维码和浏览器状态；
- kill cloudflared 等到新 quick URL，固定书签恢复且旧 target 不再使用；
- 阻断 register/代理时界面能区分 relay 与 tunnel，quick 不被重启，裸 quick 回退可用；
- 关闭 relay、切 named、停止公网均只发一次注销，失败不阻塞本地停止，之后无心跳；
- 重置身份得到新地址，旧地址被撤销，界面明确要求重新配对；
- 日志和打包诊断中敏感值出现次数为 0；C、frp、LAN、Tailscale 的配对和开关回归通过。

**退出/回滚条件**

任何 secret 泄露、旧 target 回写、Worker 故障拖垮 quick 或旧路线回归失败，都不发邀请版本。用户侧回滚为关闭 relay 或回退插件版本；保留身份文件以便向前恢复，不能借回滚清掉身份后悄悄换固定地址。

### Phase 4：Free 邀请制内测（第 9～12 周，12～18 人日）

**目标**

证明我方不仅能部署，还能准入、观察、撤销、回答用户问题和停止服务。默认仍关闭，不开放匿名注册。

**分批**

1. 第 9 周：5–10 个明确邀请实例，覆盖 Windows/macOS、4G/5G/Wi-Fi、至少两类真实网络；
2. 第 10 周：集中修复与演练，不为凑人数扩量；
3. 第 11～12 周：仅在门槛全过后扩到不超过 25 个实例；100 个中度活跃实例只是 Free 容量软线，不是本阶段目标。

**交付物**

- 邀请发放/停用、每邀请额度、id 撤销、关注册和全局停用的运营手册；
- Cloudflare 指标 + 外部 `/health` 探测 + 至少一条真实 quick 全链路探测；每日低基数汇总和异常告警；
- 控制面全量脱敏日志，数据面错误日志和约 1% 采样；SSE/WS 不按消息记日志；
- Free 配额、staging 配额耗尽演练、账号用量日报和升级触发检查；
- 客服入口与四类标准处理：连不上、地址/Origin 变化、撤销/泄露、Cloudflare/地区网络不可用；
- 隐私政策与条款审查清单、数据保留初版、事件联系人和回滚公告模板。

**最小初始政策（估算，发布前需确认平台能力和合规文案）**

- 数据面安全日志尽量只留错误与采样，原始安全日志目标不超过 7 天；低基数聚合目标 90 天；
- target 过期即不可用，disabled 记录在 24 小时内清理临时 Origin；
- 90 天无任何活动的身份先冻结并通知，再按已公布政策删除；不照搬参考项目的静默 90 天 GC；
- 用户删除请求先撤销入口，再删除身份、邀请关联和可定位日志；备份/平台保留周期必须核实后写入政策，不能承诺“立即从所有备份消失”。

**验收标准**

- 5–10 个实例连续 7 天、扩量后连续 14 天：无未解决 P0/P1 安全问题；剔除计划断网后，全链路成功请求占比 ≥99%，CPU/SSE/WS 达到 Phase 2 门槛；
- 在至少两个网络位置执行撤销，达到同节点 10 秒、跨节点 90 秒目标或触发告警/紧急阻断；未达标不得宣称即时撤销；
- staging 跑到 Free 处置点：60k 告警、80k 后新业务受限，unregister/admin 仍可用；恢复流程有记录；
- 关闭新注册、单 id 撤销、全局停用、恢复上一 Worker 版本各演练一次，记录实际生效时间；
- 所有邀请问题都能归入故障分类并有处理结果；内测支持响应目标为下一个工作日，不承诺解决时间；
- 数据保留、隐私、Cloudflare 条款与国内合规没有未处理的阻断项。

**退出/回滚条件**

出现明文敏感日志、公开代理、无法撤销、持续 CPU 超限、失控滥用或客服/故障超出人力，立即停止扩量。按影响范围依次选择：停新邀请 → 撤销异常 id → 限制重度流量 → 全局停代理；电脑端引导裸 quick/C/frp，明确旧固定书签不会自动换源。

## 5. 运营后台最小集与演进

### 5.1 近期最小集：Access admin API + CLI

参考项目没有这套后台，我们不能照搬其“插件自服务 + 控制台”作为公开产品的运营方案。

| 能力 | 近期必须能回答/执行 | 实现约束 |
|---|---|---|
| 实例列表 | 按 id、状态、邀请、最后心跳筛选；看 target 年龄而非泄露完整 target | 分页；管理视图也不默认显示 secret、手机 token、query |
| 用量 | 日请求、错误、429、长连接估计、上传量、近 7 日趋势 | 来自平台指标和每日聚合，不每请求写 D1 |
| 单 id 处置 | suspend、revoke、恢复非泄露 suspend；必须填 reason | revoke 是终止性操作，保留墓碑，不能重新认领 |
| 注册开关 | 关闭新邀请/新身份，保留已有心跳与注销 | 与全局代理开关分开，避免一个按钮误伤全部用户 |
| 全局停用 | 数据面停止代理并显示安全离线页；管理面仍可用 | KV 软开关之外保留“部署 deny-all/平台 Host 阻断”的紧急硬开关 |
| 审计 | 谁、何时、对哪个 id、做了什么、为什么、结果如何 | CLI 和页面共用 API；不允许绕过 API 直接改库而不留审计 |
| 健康/告警 | Workers、D1/KV、撤销失败、target 过期、套餐阈值 | 公共 `/health` 不暴露逐 id 信息，深度检查仍在 Access 后 |

CLI 是近期主要操作界面，简单页面只用于只读列表和状态也可以；不要为了“看起来产品化”先做复杂前端。高风险动作需要二次确认和明确影响说明。Cloudflare 控制台是应急工具，不是日常无审计写入口。

### 5.2 远期演进

按运营量而不是按功能欲望排序：

1. **可视化与告警**：实例详情、版本分布、错误时间线、配额编辑、撤销任务状态、告警确认与值班交接；
2. **按 id 产品配额**：日请求、并发、长连接、文件字节数，支持 Free/Paid 套餐覆盖；配额变更有审计和生效范围；
3. **工单/客服**：把 invite/id 的散列、插件版本、最近错误和处置记录关联到工单，用户可一键导出脱敏诊断；
4. **数据权利**：身份/用量导出、自助删除、删除任务进度、备份到期证明和法律保留例外；
5. **安全运营**：密钥轮换、异常画像、滥用规则版本、管理动作双人复核（仅高风险动作）、安全事件时间线。

触发可视化后台的建议条件：周均运营动作超过 30 次、两人以上值班或 CLI 已造成操作等待/误操作风险。未达到前，优先补可靠 API 和审计，不提前养一套后台前端。

## 6. 远期计划（3～12 个月）

远期每项都有进入条件，不是默认全做。

### 6.1 Paid 扩容、配额与计费（3～6 个月）

- 达到第 8 节升级触发后先开 Workers Paid，保持邀请/限量，观察至少一个完整账期；不是开 Paid 就立即公开注册。
- 用实际控制台数据拆分 Workers 请求、CPU、KV/D1、日志、长连接和文件流量；修正 442 模型与配额。
- 严格全局配额若需要一致计数组件，应单独评估小型 quota 组件；它与 DO bridge 是不同决策，不能为了计数顺带引入整套 bridge。
- 计费只在有真实单位经济、退款/超额规则、发票与运营主体确认后做。收费前必须定义：套餐包含量、超额是限速还是收费、长连接和文件是否单列、服务停用后的数据删除。
- Free 可继续作为邀请/体验层，但不承诺永久免费；若 Free 持续补贴且没有明确产品价值，可停止新 Free，而不是无限扩容。

### 6.2 审计、滥用治理与密钥轮换（3～9 个月）

- 从单条限流升级为风险画像：新邀请突增、鉴权爆破、目标频繁变化、异常大文件、长时间高带宽、恶意扫描和投诉；
- 处置分级为观察、限速、suspend、revoke、关闭邀请、全局停用，并保留申诉/误封恢复流程；
- server pepper 采用版本化轮换，支持旧哈希校验后异步升级；轮换演练不能使全部实例同时失效；
- secret rotate 需旧 secret 鉴权、原子换哈希和撤销旧值，不与“重置固定地址”混为一谈；
- 管理权限按人/角色拆分，定期复核 Access 和 service token，离职/泄露可单独撤销。

### 6.3 SLA、状态页、数据保留与合规（4～12 个月）

- 状态页分开显示“我方控制面”“我方 Worker 数据面”“Cloudflare quick 依赖”，避免 quick 故障被我方整体 200 健康页掩盖；
- 只有在至少 30 天真实 SLO、值班和故障复盘成立后，才讨论 Paid SLA。SLA 只覆盖我方可控边界，不能把用户电脑、家庭宽带或 quick 承诺成 99.9%；
- 建立数据目录：identity、invite、target、审计、运行日志、聚合指标、客服附件分别列目的、保留期、删除方式和跨境路径；
- 提供可验证的导出/删除流程，定期清理过期身份和日志，检查备份生命周期；
- 面向中国大陆公开服务、收费或扩大数据类型前，分别确认 ICP/备案、公安联网备案、经营许可、个人信息和跨境要求。工程方案不代替法律意见。

### 6.4 是否引入 B / claim

**默认不引入。**只有同时满足以下条件才做 10～20 实例 canary：

1. 连续 4 周数据表明 quick 是主要故障源，例如 quick 归因的不可用实例日 >2%，或每月出现两次以上影响面明确的 quick 事件；
2. 命名隧道 canary 能把全链路失败率至少改善 1 个百分点，且延迟、客服量和成本没有更差；
3. 已有账户级 API 最小权限、资源清单、token 保管、release/retire、孤儿 Tunnel/CNAME 对账和回收演练；
4. B 的账户资源成本与责任有人承担，用户能分清 B 与 C，不把现有 C 用户静默迁移。

若只是偶尔 quick URL 改变，A 已能保持固定地址，不构成做 B 的理由。若 B 仅在少数高价值用户有效，可作为单独付费/托管选项，不替换 A。

### 6.5 是否引入 DO bridge

**默认不引入。**bridge 的候选理由必须是不能由 A/B 更好解决的传输问题，而不是“参考项目已经有”。

进入 canary 前至少要求：

- quick 和 named 都已用数据排除，或明确存在必须自建 connector 才能满足的产品需求；
- 帧协议有版本、鉴权、背压、流上限、重连、幂等、异常关闭和升级兼容设计；
- HTTP/SSE/WS/50 MiB 文件、弱网和多地区 30 天 canary 通过，且 p95、错误率和单位成本优于现有路线；
- 保留按 id 切回 quick 的能力，旧插件仍可运行；DO 故障、对象迁移和 connector 重复连接有演练；
- DO 请求/时长/存储账单已有小流量实账，不用“长连接不占 CPU”推导“bridge 一定便宜”。

仅为了全局计数，不引入 bridge；仅为了 E2EE，也不引入 bridge，因为 Worker/DO 仍可能看到明文。

### 6.6 多区域、国内替代与 frp 协同（6～12 个月）

- Cloudflare 的任播不等于我方可承诺数据驻留或中国大陆体验；先按地区记录首连、首字节、SSE/WS 和错误率，再决定是否多区域控制面/日志。
- 国内托管中继如果要做，应复用“固定入口、邀请、撤销、配对状态”的产品经验，但单独评估服务器、带宽、备案、数据跨境和运营，不是把 A 的 target 白名单改成任意 VPS。
- 现有 4 Mbps 自建服务器只继续承担单人验证；正式国内服务需要独立容量评估，不与原站抢带宽。
- 自建 frp 保持用户自控选项。可共享配对展示和诊断格式，但不要求用户把服务器凭据交给我方。
- 不做 A ↔ frp ↔ C 的自动热切换：不同 Origin 会改变 Cookie/书签，自动跨境还会改变数据路径。可以提供“检测多条路并建议用户切换”，切换必须由用户确认并重新配对。

A 的边界始终是“低门槛的我方运营入口”，不是全球统一隧道平台，也不是所有网络条件下的默认最优解。

## 8. 容量与单位经济

### 8.1 计费基线与模型边界

以下沿用现有方案的规划基线，均为 **[估算]**，不是参考项目账单，也不是实时官方报价：

- Workers Free：100,000 请求/天、10 ms CPU/请求；
- Workers Paid：5 美元/月、含 10,000,000 请求/月；
- KV、D1、DO、日志/分析、超额请求和增值功能另核；上线前以我方控制台和当前官方文档为准。

理论实例数 = 请求额度 ÷ 单实例请求量；建议容量 = 理论值 × 70%，预留突发、重连、监控和模型误差。Paid 按 30 天，不把 1,000 万当日额度。

### 8.2 模型一：我们的 15 分钟心跳模型

定义“活跃实例/日”：电脑全天在线，手机中度使用。

| 来源 | 假设 | 请求/实例/日 |
|---|---|---:|
| register 心跳 | 每 15 分钟一次 | 96 |
| 固定地址端到端健康检查 | 每 15 分钟一次，经 Worker | 96 |
| 三次冷加载 | 75 个页面/静态/API 请求 | 75 |
| 普通业务 API | 日累计 | 165 |
| SSE/WS 建连和重连 | 日累计 | 10 |
| **合计** | 后台 192 + 用户流量 250 | **442** |

该模型的 45 分钟 TTL 让崩溃实例最多约 45 分钟后停止代理，身份仍归原 secret。它购买的是可预测的离线语义，不是单纯增加开销。

### 8.3 模型二：参考项目的启动注册模型

参考客户端没有 15 分钟心跳，Worker 以 90 天 last_seen 做 GC。为可比较，作如下显式假设：

- 用户流量仍取同一中度画像 250 请求/日；
- 每天一次启动登记 + 一次 target 变化登记，共 2 个 Worker 控制请求；
- 不把不经 Worker 的 quick 直连探测计入；模型假设没有我们的 96 次固定地址周期探测。

则规划量为 **250 + 2 = 252 请求/实例/日**。若整天不启动也不变化，则接近 250；实际重试和重连会增加。

**较低请求量不代表语义等价。**没有周期心跳和短 TTL 时，崩溃后的旧映射可能保留到 90 天 GC，在线新鲜度依赖 quick 上游失败和下一次启动登记。不能为了容量好看就照搬。

### 8.4 两种模型的容量对照

| 模型 | 请求/实例/日 | Free 理论 / 70% 建议 | Paid 理论 / 70% 建议（30 天） |
|---|---:|---:|---:|
| 我们的心跳模型 | 442 | 226 / **158** | 754 / **528** |
| 参考启动注册模型 | 252 | 396 / **277** | 1,322 / **925** |

解释：

- 100 个中度活跃实例在我方模型下约 44,200 请求/日、约 132.6 万请求/30 天；这只是 Free 软容量，不是首发人数。
- 我方模型 528 个建议实例约 699 万请求/月，恰好接近 Paid 软线；重度文件/远程窗口用户会显著降低可承载实例数。
- 参考模型 925 个建议实例也约 699 万请求/月。控制面差异会改变容量，但用户流量仍是主要变量之一。
- 请求模型没有完整表达文件字节数、SSE/WS 持续时间、CPU 和客服量，因此不能单独用来定价。

后续可通过真实数据调整健康检查频率，但任何减量都要同时评估离线发现时间，不直接换成 90 天 TTL。

### 8.5 Free / Paid 软线、硬处置线与升级触发

| 层 | 软线 | 硬处置线/动作 |
|---|---|---|
| 单 id | 1,500 请求/日，记录并观察 | 5,000/日后限新业务 429；注销/管理始终可用 |
| 单 id 突发/连接 | 120 请求/分钟；8 条 SSE/WS；2 个大文件上传 | 超限 429 或拒绝新 Upgrade；不批量强杀已有流 |
| 全局 Free | 60,000/UTC 日告警、停止新邀请评审 | 观测到 80,000 后限制新业务，给健康/注销/管理预留约 20,000 |
| 全局 Paid | 700 万/月，扩容与预算评审 | 850 万/月停止新注册并限制异常重度 id；超额预算/扩容必须先批准 |

这里的 80k/850 万是**运营处置阈值**，不宣称恰好第 80,001 个请求一定被全局一致拦截。平台计数有延迟，KV 不是全局原子计数器。上线前必须核实 Cloudflare 原生限流能否按 Host/id 执行；无法精确执行的部分，用邀请名额、保守余量、日聚合和自动停量兜底。需要精确硬配额时另建一致计数组件并重新压测。

**Free→Paid 触发，任一满足即评审：**

- 连续 3 天超过 60,000 请求/日；
- 近 7 日均值预测 30 天超过 **210 万**请求（Free 100k/日的 30 天等效为 300 万，提前到 70% 评审；这不是实际 Free 月额度）；
- 中度活跃实例持续超过 100，或高价值用户已愿意为稳定性付费；
- CPU、错误率、长连接、D1/KV 或客服量先达到风险线，即使请求数没到也要评审。

**Paid 扩容触发：**700 万/月软线、普通代理 CPU p95 >7 ms 持续 15 分钟、频繁 10 ms 超限、5xx/429 异常或长连接大面积掉线，任一均触发。850 万以后不能继续无预算透支。真实用量未降回 Free 前，Paid 不能直接降级回 Free，否则回滚本身就是故障。

### 8.6 SSE / WS / 文件对模型的影响

- 一次 SSE 建连或 WS Upgrade 先按一个 HTTP 请求规划，流内消息不当作新 HTTP 请求；每次重连另计。实际计费以当前规则复核。
- 等待网络不等于同墙钟 CPU，但逐帧处理、缓冲、解压、序列化和详细日志会增加 CPU/持续时间风险。
- 普通代理热路径只做 target 读取、头处理和流式返回；HMAC 在低频控制面，不在每个手机请求计算。
- 远程窗口和文件可能让“请求数很少、字节数很大”。Paid 前必须增加带宽/字节、连接时长和重连率三个视图。

### 8.7 成本项与预算区间

以下是预算占位 **[估算]**，不是 Cloudflare 或人力报价；区间用于避免把成本写成 0，也不能拿去对外承诺。

| 成本项 | 邀请内测 | 早期 Paid | 说明 |
|---|---:|---:|---|
| 域名/DNS/TLS | 普通域名约 US$10–40/年；复用现有域名时增量更低 | 同左，另留 DNS 增值服务可能费用 | 不含溢价域名；先验一层通配证书 |
| Workers | Free 可为 0 | 规划基线 US$5/月起，先留 US$5–50/月基础预算 | 超额、增值项按控制台另算，不编精确账单 |
| D1 / KV / Cache | US$0–20/月占位 | US$0–100/月占位，按真实读写/存储修订 | Cache API 不另当数据库；心跳也产生控制面读写 |
| DO | 近期不引入，预算 0 | 只有 quota/bridge canary 后另列 | 不用未知 DO 单价填假账单 |
| 日志/分析/外部监控 | US$0–50/月 | US$20–200/月 | 采样、保留期、通知和真实链路探测决定成本 |
| 工程运维人力 | 建设 53–76 人日；运行约 2–5 人日/月 | 初期约 5–15 人日/月 | 含部署、值班、撤销、复盘；重大事件另算 |
| 客服 | 内测可并入上述 2–5 人日/月 | 每活跃实例先按 5–15 分钟/月观察，再按工单实测 | 连接、重配、地区网络、隐私/删除是主要类别 |
| 合规/法务/财税 | 无法可靠估价，单独立项 | 收费/公开前必须有预算 | 不用“备案免费”推导全部合规成本为 0 |

建议同时看三个单位经济指标：

```text
每千请求基础设施成本 = 当月可归因基础设施费 ÷ 请求数 × 1000
每活跃实例总成本     =（基础设施 + 监控 + 运营/客服人力成本）÷ 活跃实例月
每付费实例贡献       = 实收收入 - 支付/税费 - 每实例可变成本 - 分摊运营成本
```

至少收集一个完整账期后再定价。若人力始终占主要成本，应优先改善诊断、自恢复和邀请范围，而不是只优化 Worker 的几美元账单。

## 9. 安全、合规与信任

### 9.1 上线前必须成立的安全边界

1. **明文可见。**Worker 与 Cloudflare 都在传输信任边界；A 不是 E2EE，告知与隐私政策一致。
2. **三类撤销分离。**插件撤销手机设备；用户 unregister 停用自己的 target；运营 revoke 切断 id。任何一类都不冒充另外两类。
3. **固定域名钓鱼。**secret 泄露可让攻击者替换已知 id 的 target，因此要有管理撤销、身份重置和重新配对提示。
4. **SSRF/开放代理。**严格 target、manual redirect、无公共 resolve、无 CONNECT、请求体/速率/并发限制缺一不可。
5. **本机路由隔离。**公网回连后 remoteAddress 可能像本机；不得仅凭 IP 判定可信。公网 Host、Forwarded 头和仅本机管理接口必须逐条拒绝测试。
6. **日志脱敏。**默认不记正文、query、Cookie、Authorization、secret、邀请明文、完整 target 或文件内容；IP 不进普通业务日志，id 用每日加盐散列做聚合。
7. **公开插件无秘密。** endpoint 可公开，邀请与管理员凭据不可嵌入；所有权限由服务端实时判断，撤销不能被客户端设置绕过。

### 9.2 隐私与数据最小化

数据面仅保留 requestId、时间、方法、路径模板、状态、耗时、CPU、字节数和散列 id 等必要字段；路径模板不能把真实 token 或文件名带进去。控制面审计只保留准入、状态和管理动作所需数据。

发布前用真实日志扫描验证，而不是只在文档中承诺。隐私政策至少说明：运营主体、数据类别、处理目的、Cloudflare 等第三方、可能的跨境、保留期、删除方式、安全事件联系方式和未成年人/敏感内容使用边界（如适用）。

### 9.3 条款与国内合规门槛

以下是工程风险清单，不是法律结论：

- 上线前审查当前 Cloudflare Workers、Tunnel/quick tunnel、可接受使用、代理/滥用、隐私、日志和套餐条款；技术可行不等于条款允许所有公共代理用途。
- Free 内测也要说明可随时停止、无 SLA、quick 依赖和不保证所有地区可达；不得宣传“永久免费”“绝不记录”“端到端加密”。
- 面向中国大陆公众、收费或规模化经营前，专业确认 ICP/备案、公安联网备案、经营许可、远程接入服务性质、个人信息和跨境要求。
- 未确认前仅做小范围邀请技术验证；大陆用户不自动切到境外或其他线路。合规不明确时，停止公开是合法产品的默认回退，不是工程失败。

## 10. 风险、触发信号与回滚

| 风险 | 触发信号 | 立即动作 | 恢复/长期回退 |
|---|---|---|---|
| Free 请求额度 | 60k/日告警；预测达到 80k/100k；429 突增 | 停新邀请和新注册，限异常 id；到 80k 处置线限新业务 | 开 Paid 或降低活跃量；保留注销/管理；不可硬撑到 100k |
| CPU/持续时间 | p95 >7 ms 15 分钟；持续 10 ms 超限；长连接掉线 | 回滚最近 Worker 变更，停高成本缓存/日志处理，限异常流量 | 降低热路径工作；未达标不扩量；必要时全停数据面 |
| D1 故障 | 注册失败率升高、管理写入失败 | 停新 enroll；不重试风暴；已有 target 按 TTL 工作 | 恢复后重放必要管理动作；身份丢失不得静默换 id |
| KV/Cache 一致性 | 新旧 target 并存、撤销超过 90 秒、陈旧记录增多 | 缩短/绕过节点缓存，重试撤销；高风险泄露用平台 Host 阻断或全局停用 | 以实测修订 SLO；读失败返回 503，不无限期吃陈旧数据 |
| SSE/WS 缓冲 | 首帧 >2 秒、成批到达、30 分钟掉线或无法重连 | 停该版本数据面或回到上一 Worker；插件标 relay degraded | 修流式/Upgrade；未通过真机前保持裸 quick/C/frp |
| quick 变化/故障 | Error 1033、target 频繁变化、DNS/TUN 失败集中出现 | 不因 relay 故障重启 quick；电脑端给替代路线，按 id 标记离线 | 达到 B 评估门槛才 canary named；A 不承诺唯一公网路线 |
| Cloudflare 整体故障 | 控制面/数据面 5xx、外部探测同时失败 | 公告依赖故障，停无意义重试；全局离线页可配置时启用 | 用户主动切已配对的 C/frp/Tailscale；旧固定书签不自动跳转 |
| 开放代理/扫描/大流量滥用 | target 异常、429、字节数或投诉突增 | suspend/revoke id、关邀请、限 body/速率；必要时全停 | 补规则和申诉流程；保留审计；未控住不公开 |
| secret/pepper 泄露 | 非预期 target 改变、鉴权异常、密钥管理事件 | revoke 受影响 id，轮换管理 token；高危时全停 | 用户重置身份并重新配对；pepper 版本化轮换和事件复盘 |
| 管理面误操作/Access 失效 | 未授权 admin 200、异常审计、误全停 | 撤 service token、关闭管理写接口；按审计恢复状态 | 修 Access、二次确认和演练；高风险动作逐步加双人复核 |
| 隐私/合规事件 | 日志发现 token/正文、用户投诉、条款或备案阻断 | 停相关日志/注册/地区服务， revoke 涉及入口，保存最小调查证据 | 删除污染数据、更新政策与产品；未获确认不恢复公开 |
| 客服/运营人力不足 | 工单持续增长、响应超过目标、值班无法覆盖 | 停扩量和邀请，降低 Free 范围，发布已知问题指引 | 优先自恢复/诊断；仍不可持续则停止 A 的新增或整体服务 |
| 单位经济不成立 | 请求达标但每实例成本/客服持续超预算 | 不新增付费承诺，冻结扩量 | 调整配额/收费；无可持续模型则保留 C/frp、关闭 A |

### 10.1 回滚级别必须提前定义

- **L1 单 id：**suspend/revoke、限制新连接，其他实例不动；
- **L2 控制面降级：**关闭新邀请/新注册，已有 active 可心跳和注销；
- **L3 数据面降级：**全局停代理或回滚到上一 Worker；电脑端提供裸 quick/C/frp；
- **L4 服务终止：**删除通配路由或部署 deny-all，保留管理读取和审计，按政策导出/删除数据并通知用户。

裸 quick、C、frp 都是**另一条 Origin 的用户侧替代**，不是固定书签的透明故障转移。任何 runbook 都不能把“插件显示新二维码”写成“手机旧书签自动恢复”。

## 11. 最终建议

### 11.1 先做哪三件事

1. **先做 Phase 0，统一 quick 生命周期。**把 originHostHeader、TunnelSupervisor、RelayProvider、代次/停止单测和旧路线回归打牢；这是 A 的地基，不是可跳过的重构。
2. **再做“窄 Worker + 最小运营控制”。**一次完成邀请准入、D1/KV/Cache、严格 target、流式数据面、Access admin/CLI、撤销/关注册/全停和审计；没有运营开关就不算 Worker 完成。
3. **最后用 5–10 个邀请实例验证服务闭环。**跑真实手机、SSE/WS、文件、故障和客服；先用首批 7 天数据决定是否扩到 25，再用扩量后的 14 天数据决定转 Paid、维持小众或停止。

### 11.2 暂时不做什么

- 不公开匿名注册，不默认给所有插件用户开启 A；
- 不做 B/claim、DO bridge、多区域、自动跨境、自动跨 Origin 热切换；
- 不做账号/计费/复杂可视化后台来替代真实用量和运营闭环；
- 不为了省请求采用 90 天在线 TTL，不为了配额在每请求写 KV/D1；
- 不承诺 E2EE、即时全局撤销、永久免费、国内必然可用或 Paid SLA；
- 不替换 C、自建 frp、裸 quick、局域网、Tailscale。

### 11.3 是否应当全量产品化

**当前答案是否定：先做有明确退出的产品化内测，不做全量公开发布。**

A 的低门槛价值真实，但它把项目从“插件”变成“持续承担安全、隐私、故障和客服的运营服务”。如果 Phase 2 无法稳定承载核心协议、撤销/条款无法过门，或内测证明 quick 故障与运营人力长期高于用户价值，就应该停止 A，而不是因为已经投入 Worker 成本继续扩张。C、自建 frp、LAN 和 Tailscale 仍是可交付的路线。

只有真实数据同时证明“用户需要、技术可靠、服务可控、成本可承担、合规可解释”，A 才进入 Free 扩量或 Paid 商业化。

## 12. 仍不确定、必须在对应阶段核实

1. 我方 Cloudflare 当前套餐、原生按 Host/id 限流能力、日志保留配置、Access 能力和实际价格；参考仓库没有账单。
2. quick tunnel 当前条款、生产可用性、目标地区网络，以及 SSE/WS/大文件在真实平台的限制。
3. KV/Cache 在至少两个网络位置的传播分布，撤销 90 秒目标是否可稳定达到；达不到时的平台级紧急阻断流程。
4. 442/252 两个模型与真实控制台请求数的偏差，尤其是健康检查、重连、远程窗口和文件流量。
5. 邀请用户的留存、支持时长、每实例字节数/连接时长，以及人力是否比云资源更早成为瓶颈。
6. 国内公开服务、收费、数据跨境和隐私文本的专业审查结论。
7. Free 后的商业形态：继续邀请免费、免费 + 付费配额，还是仅面向已有用户增值服务；在单位和用户价值数据出来前不预设。

这些不确定项都有明确的核实阶段，不应通过照抄参考项目、提前公开注册或编写精确账单来掩盖。
