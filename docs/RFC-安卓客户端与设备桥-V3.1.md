## 0. 结论先行

三个可以独立停下来的阶段：

| 阶段 | 交付物 | 需要无障碍权限吗 | 面向谁 | 单独有没有价值 |
|---|---|---|---|---|
| **P1 遥控器客户端** | 原生壳 + 锁屏也能收到的审批/完成通知 + 通知里直接批准 + 系统分享到 DSH | **不需要** | 所有现有手机用户 | 有。补上网页锁屏后断连这块硬伤 |
| **P2 轻手机桥** | 电脑把东西**送到**手机：通知、链接、文件、剪贴板 | **不需要** | 所有人 | 有。覆盖“电脑 → 手机”八成真实诉求 |
| **P3 手机操控（实验）** | 电脑看屏幕、点按、输入 | **需要**，单独的构建版本 | 明确选择加入的进阶用户 | 有，但前提是 P0 探针与 P3 闸门都通过 |

v3.1 相对 v3 的八处实质改动（前六条从 v3 继承，后两条是本轮新增）：

1. **配对二维码是“一址一码”**，不是“一个码带多条地址”。客户端扫任意一枚之后，必须调插件的地址池接口拿全路径（接口见第 11 节）。
2. **配额数字先别写死**：10 万是 Workers 的原始日额度（请求/读取各一份），5 万是“每次代理读两次 KV”推导出的代理请求上限——**单位不同，不是两个候选值**。v3.1 按这个口径写，并把当期真实额度标为待核实。
3. **共享固定地址上的手机桥改为“提示 + 硬上限”**：每台设备每天走共享路径的武装总时长不超过 2 小时（由 A 端按 `bridgeId` 记账、UTC 日界、跨重启累计），超出即提示改走 Tailscale 或专属地址。
4. **B 端不纳入武装制**：B 端是“配对一次长期在线”的既有产品体验，保持现状，只加监控。
5. **第 14 节的问题已拍板**（见第 14 节），不再留给决策者。
6. **地址池接口**：`GET /mini/api/addresses`，只返回地址与类型，不含令牌（见第 11 节）。
7. **配对必须能换到设备凭据（v3.1 新增）**。二维码里装的是 5 分钟一次性 grant，不是设备凭据；v3.1 新增一个**消费 grant 的原生配对接口**，在同一响应里返回设备凭据（`id.密钥`，`kind: android-app`）、地址池与公钥元数据。没有它，P1 的第一步就走不通。
8. **触摸规则统一（v3.1 新增）**。v3 一边说“降级为辅助信号”，一边又把它列进“立即作废”，自相矛盾。v3.1 把它从作废清单里拿掉，只作为 P0 的观测指标；收回授权靠四个确定性条件：锁屏、离开授权 App、用户点停止、5 分钟无注入动作。

## 1. 这份 RFC 依赖的项目事实

| 事实 | 出处 | 对本 RFC 的影响 |
|---|---|---|
| A/B 协作用 **HTTP 长轮询**：B 出站连 A，单次轮询最长 25 秒，任务默认 30 秒超时，90 秒没轮询算离线，配对码一次性、10 分钟有效 | `lib/agent-hub.js` | 手机桥直接复用这套模型，不新造协议 |
| 设备凭据是 `id.密钥`（各 128 位），服务端只存 SHA-256；可用 cookie `dsh_mini_device` 或请求头 `X-Mini-Device` | `lib/devices.js` | 原生层直接用请求头 |
| 设备名册**最多 5 台**，30 天没活动自动删除 | `lib/devices.js` | 同一部手机的浏览器和 App 各占一格 |
| 审批/提问归属：手机 SSE 连着，**或** 20 秒内露过面，就算“手机在”；全断开就还给电脑 | `lib/server.js` | 客户端后台保活会改变这个语义（见 5.2） |
| 审批接口 `POST /mini/api/approval {id, decision}`，已结束的审批返回 409 | `lib/server.js` | 通知按钮可直接调，但**必须带上审批 id**（见 5.3） |
| 已有外部推送：Bark、ntfy、Telegram，标题固定“DSH 任务完成” | `lib/notify.js` | 只覆盖“任务完成”；**审批/提问的 `onPending` 目前只接了飞书**（见 5.3） |
| 网页的 Service Worker 只发系统通知，且要求 HTTPS | `lib/sw.js` | 明文内网下网页拿不到通知，这正是客户端的价值 |
| A/B 的信任假设是“A 是用户自己的电脑，防误操作，不防恶意” | `lib/agent-client.js` | **C 端不能照搬**：A 上的模型会读到不可信内容 |
| 共享固定地址每个代理请求都消耗 Worker 与 KV 配额。免费版原始额度是 **10 万请求/读取**（请求与读取各一份）；按“每次代理读两次 KV”推导，**代理请求上限约 5 万/日** | `docs/A-承载量估算.md`、运维后台 | 两个数字单位不同，不能当“5 万还是 10 万”二选一（见 6.5） |
| 配对面板是**一址一码**：内网、Tailscale、隧道各生成一个二维码 | `lib/pairing.js` | 客户端不能假设码里有全部路径，需地址池接口（见 5.4） |
| 二维码里装的是 **5 分钟一次性 grant**，不是设备凭据；现有 `/mini/pair` 只发短期 token cookie 并跳转，设备凭据要到打开 `/mini` 时才登记发放 | `lib/server.js`、`lib/devices.js` | **原生层无法只靠扫码拿到 `id.密钥`**——P1 必须新增原生配对接口（见 5.1、11） |
| 地址池实际在 `lib/index.js` 里组装，`lib/pairing.js` 只负责给每条地址画码 | `lib/index.js`、`lib/pairing.js` | 第 11 节改动清单要把 `lib/index.js` 算进去 |
| 目前**没有**对外的“地址池”只读接口；设置页是在进程内直接调 | `lib/pairing.js`、`lib/index.js` | P1 需要新增一个只读接口（见 11） |

## 3. 设计原则

1. **灵魂在电脑**：推理、上下文、编排都留在 A。不在手机上跑 DSH、Linux 或模型。
2. **手机是最终裁判，裁判本身也要防篡改**：确认环节不能被本 App 的无障碍能力点掉，也不能被中继伪造的指令触发。
3. **能“送达”就不“操控”**：能通过 Intent、通知、文件或剪贴板完成，就不走 GUI 自动化。
4. **权限按构建版本隔离**：标准版永远不声明高危权限。
5. **网页是唯一的 UI 实现**：原生层只做网页做不到的事。
6. **不承诺 24 小时保活**：只在有任务或桥接开启时保活。
7. **共享中继配额是公共资源**：任何常驻轮询都要算账。
8. **不可靠的信号不当硬规则**（v3 新增）：ROM 上验证不了的能力，只能当辅助判断，并配一个确定性的兜底。

## 5. P1：遥控器客户端

### 5.1 形态（置信度：高）

WebView 承载现有页面，Kotlin 原生层只做五件事：

| 原生职责 | 实现要点 |
|---|---|
| 扫码配对 | CameraX 识别配对 URL（里面是**一次性 grant**，不是设备凭据）→ 调原生配对接口 `POST /mini/api/native-pair`，用 grant 换回 `{deviceId, deviceSecret, addresses, keyId, keyFp}` → 密钥存进 Keystore 加密存储 → 按当前地址写入 WebView 的 CookieManager |
| 地址池 | 配对响应里直接带回；之后按“内网 → Tailscale HTTPS → 固定地址”探测 `/mini/api/version`，失败换下一条，切换时重新加载 WebView |
| 通知 | 见 5.3 |
| 快捷审批 | 通知按钮直接 `POST /mini/api/approval`，请求头带 `X-Mini-Device`，请求体带**审批 id**；409 时把通知改成“已在别处处理” |
| 系统分享 | 接 `ACTION_SEND` / `ACTION_SEND_MULTIPLE` → 走 `/mini/api/upload` 与 `/mini/api/send` |

**原生层不另起一条长连接去同步页面状态**：前台时只有 WebView 自己连 SSE；后台时由通知通道负责（5.3）。

**Cookie 的两个坑（v3.1 补）**：

1. Cookie 按**主机名**隔离，不按“同一台电脑”共享。扫内网 IP 写下的 Cookie，切到 Tailscale 或固定地址域名后不会自动带上。做法是每次选定地址后，**用该地址的 base URL 单独调一次 `CookieManager.setCookie`**：省略 `Domain`、`Path=/mini`、`HttpOnly`、`SameSite=Lax`；只有 HTTPS 地址才加 `Secure`（`SameSite=None` 会强制要求 `Secure`，不能用它绕过 http）。
2. 明文 HTTP 会被系统拦。targetSdk ≥ 28 默认禁止明文流量，内网首页可能直接打不开。需要在网络安全配置里**显式放行已配对的内网地址**，并用 WebView 导航白名单限制范围；Tailscale 与固定地址仍强制 HTTPS。

原生层的所有自身请求（审批、配对、上传）一律走请求头 `X-Mini-Device`，不依赖 Cookie，避免上面两个坑。

### 5.2 审批归属语义（置信度：高，**已拍板**）

**问题**：`hasPhone()` 的判据是“SSE 连着，或 20 秒内露过面”。客户端后台保住连接后，手机永远“在”，审批不会还给电脑，人锁屏放兜里时电脑会一直卡着。

**方案**：客户端上报两个独立状态，服务端分开判断：

- `attention = foreground`：用户正在看，行为与现在的网页完全一样。
- `attention = reachable`：在后台，但能收到通知。

`hasPhone()` 规则：

- `foreground` → 算在场。
- `reachable` → 由新设置项「审批优先发到手机」决定。**默认关**；打开时手机上最多等 **120 秒**，超时还给电脑。

改动范围：`lib/server.js` 的 `hasPhone()` / `notePhoneSeen()`，`/mini/api/presence` 增加字段。网页版行为不变。

### 5.3 后台唤醒通道（置信度：中，【待真机验证】）

不做 24 小时保活，按场景分三层：

| 场景 | 唤醒方式 | 说明 |
|---|---|---|
| 有任务在跑或有待审批 | 任务期间开启的前台服务（`dataSync`），保持一条 SSE | 任务结束后 60 秒内自动停止；**Android 14+ 需同时声明 `FOREGROUND_SERVICE` 与 `FOREGROUND_SERVICE_DATA_SYNC`；Android 15 起 `dataSync` 每 24 小时累计最多 6 小时**，超时要在 `onTimeout` 里几秒内停掉并退回 ntfy，长任务不能无限依赖这条 SSE |
| 空闲时 | 复用 `lib/notify.js` 的 **ntfy** 渠道；**优先建议用户自建 ntfy 实例** | 公网 `ntfy.sh` 在国内可达性不稳，且内容对服务方可见 |
| 以上都没有 | 只在打开 App 时同步 | 明确告诉用户“空闲时不会主动提醒” |

**插件配合（v3.1 补全）**：

- 推送按事件类型区分（待审批 / 被提问 / 完成），正文去敏；
- **payload 必须带 `approvalId`**（审批/提问的 id）与会话 id——没有它，通知栏的“批准”按钮不知道批哪一条；
- **要接在 `lib/index.js` 的审批/提问回调上**：现有 `notify.js` 只在任务完成时被调用，审批/提问的 `onPending` 目前只接了飞书，只改 `notify.js` 不会产生待审批通知；
- 推送正文不能带审批详情（公共 ntfy 能看到内容），只发“有一条待审批”，点开后再用设备凭据拉详情。

**ntfy 不是可靠的唤醒通道**：走 UnifiedPush 时需要 ntfy 分发器在场，用户卸载分发器、国产 ROM 限制自启动/后台联网、电池策略都会让它失效。因此“空闲时能收到提醒”只能定位为**尽力而为**，启动时要处理 `UNREGISTERED / REGISTRATION_FAILED`，失效时把 `reachable` 置假并引导用户重装分发器。

**【待真机验证】**：ntfy / UnifiedPush 在小米、vivo、OPPO 后台的存活率与延迟分布，P0-b 实测。

### 5.4 地址池

配对面板是**一址一码**：内网、Tailscale、隧道各一枚。因此客户端流程是：

1. 扫任意一枚码，拿到一次性 grant；
2. 调原生配对接口换设备凭据，**响应里同时带回地址池**（v3.1 改为随配对返回，减少一次往返）；
3. 按池顺序探测 `/mini/api/version`，选第一条通的作为当前地址；
4. 之后网络变化时按同一池重新探测；需要刷新时调 `GET /mini/api/addresses`（见第 11 节）。

两个接口都只返回地址与类型标签，**不返回令牌**（令牌只在设备凭据里）。

### 5.5 设备名册占位

同一部手机上浏览器和 App 各占一个名额（上限 5 台）。登记时 `kind` 记 `android-app`，设置页显示“某某手机（App）”。不与浏览器身份合并（`devices.js` 的原则是“不用指纹认人”）。

### 5.6 P1 验收（真机，不接受模拟器）

一台未开开发者模式的量产小米（澎湃 OS）+ 一台 vivo 或 OPPO：

1. 从浏览器下载 APK 安装，记录系统拦截次数与位置；标准版要求 **0 次“高危权限”警告**。
2. 扫码连上 A，三档视图可切换。
3. 切到 5G、离开家里 Wi-Fi：WebView 10 秒内自动切到 Tailscale 或固定地址，不需重新扫码。
4. **（设置开启时）**「审批优先发到手机」打开、A 发起需要审批的任务后锁屏：前台服务存活，手机 **5 秒内**亮屏弹通知；点“批准”后 A 继续；同一条审批已在电脑处理时，通知显示“已在别处处理”。
5. 从相册分享一张图给 DSH：A 当前会话收到图片并能回答内容。
6. **（设置关闭时）** 默认状态下同一场景：审批**不给手机**、不推待审批通知，20 秒后按现有逻辑还给电脑（回归用例，行为与网页版一致）。

## 6. 手机桥通用层（P2 与 P3 共用）

### 6.1 传输：复用长轮询（置信度：高）

新增 `phone-hub`，复制 `agent-hub` 的模型：

- 配对：A 生成 6 位配对码（10 分钟有效），手机提交后换长期凭据；服务端只存哈希。
- 取任务：手机 `POST /mini-remote/phone/poll` 长轮询，单次最长 25 秒。
- 回结果：`POST /mini-remote/phone/result`，带 `taskId`；只认发起任务的那台手机。
- 大块数据**两个方向都要**（v3.1 补）：
  - 手机 → A：`POST /mini-remote/phone/blob/<taskId>`，二进制请求体（上传截图、文件）；
  - A → 手机：`GET /mini-remote/phone/blob/<blobRef>`，设备凭据鉴权、绑定 `taskId`、单文件上限、有效期 10 分钟、取一次或到期即删。
  - 没有下行这一条，`phone_send_file`（电脑把文件送到手机）在协议上根本不成立。

不用 WSS：现有四种通路都已验证能跑长轮询；Worker 中继的 WebSocket 验收在运维手册里仍标“未完成”。

### 6.2 消息格式（置信度：中）

JSON-RPC 2.0，方法名复用 MCP 的 `tools/list`、`tools/call`、`notifications/cancelled`，schema 用 `inputSchema`。**不实现完整 MCP 握手**，只复用语义。

握手时手机上报：

```json
{"bridgeProtocol":1,"appVersion":"0.1.0","flavor":"standard","sdk":34,"tools":["phone_notify","phone_open_url"]}
```

插件按 `bridgeProtocol` 判断兼容性：不兼容就拒绝，并提示“请升级客户端”。不用版本号字符串比较。

### 6.3 工具命名（置信度：中）

用 `phone_*`，不用 `c_*`。`c_` 对模型没有语义，同时看到 `b_read`、`c_tap` 更容易选错。内部文档可继续叫“C 端”。

### 6.4 工具可见性

只有“桥在线”且“用户在手机上武装了桥接”同时满足，`phone_*` 才注册给模型；其他时间模型看不到，不浪费上下文。

### 6.5 武装与配额（置信度：高，**数值待核实**）

**账**：一台手机每 25 秒轮询一次，一天约 3456 个请求。按“代理请求上限约 5 万/日”算，十几台常驻就能吃满；改用原始额度 10 万算则是二十多台。两个数字单位不同（原始请求/读取 vs 代理请求），**估算时必须用同一个口径**。

因此不按“台数”写死规则，按比例与时长控制：

- 桥接默认**不轮询**。用户在手机上点“允许电脑使用手机（30 分钟）”后才开始；到期或任务结束空闲 10 分钟后自动停止。
- **走共享固定地址时**：设置页明确提示“会占用共享额度”，并建议改走 Tailscale 或专属固定地址。
- **硬上限**：走共享地址时，**每台设备每天（UTC 日界）走共享路径的武装总时长 ≤ 2 小时**。
  - **由 A 端执行**（不是客户端自觉）：按 `bridgeId` 持久化当日累计时长与轮询次数，跨重启、跨地址切换都累计；超额直接拒绝武装并说明原因。
  - 只限单台挡不住“很多台一起用”，所以另加**全局日预算**：共享路径的轮询请求达到额度阈值（建议 80%）时，新武装一律引导到 Tailscale / 专属地址。
- **配额口径待核实**：把“原始额度”和“按实际 KV 读取次数折算的代理上限”在运维台核对一次，写进文档后再调阈值。
- **A 端改动**：运维台加“长轮询请求占比”一项（该实现属私有服务端，不进公开仓库；公开文档只写“需要匿名聚合指标”）。

## 7. P2：轻手机桥（不需要无障碍）

### 7.1 安卓限制（置信度：高）

- Android 10 起，App 在后台**不能主动打开界面**；“打开链接”只能发通知由用户点击。
- Android 10 起，后台**不能读剪贴板**；写入可以，Android 13 起系统提示“已复制”。
- 文件写到“下载”目录用 MediaStore，不需要存储权限。

### 7.2 工具集

| 工具 | 作用 | 用户需要做什么 |
|---|---|---|
| `phone_notify(title, body, url?)` | 发通知；带 url 时点通知打开链接 | 看一眼或点一下 |
| `phone_send_file(name, blobRef)` | 存到“下载/DSH”，并发通知 | 点通知打开 |
| `phone_set_clipboard(text)` | 写剪贴板并发通知“已复制” | 粘贴 |
| `phone_status()` | 电量、网络类型、是否锁屏、前台是否本 App | 不需要 |

明确**不提供**：读剪贴板、读短信、读通知、读相册。要拿手机数据，一律由用户主动通过系统分享发给 DSH。

### 7.3 安全级别

P2 工具只“送达”，最坏后果是骚扰与剪贴板被覆盖。但**剪贴板单次就可能出大事**：模型读到不可信内容后，可以把转账地址或命令替换成攻击者的，而用户粘贴时未必细看。所以：

- `phone_set_clipboard` **每次写入都要在手机上弹确认**（显示内容摘要，用户可展开看全文），不做“连续 5 次才问”的频率限制；
- 其余工具（通知、存文件、状态）武装期间可直接调用，每次写手机本地审计。

### 7.4 P2 验收

1. A 上说“把刚才那份报告发到我手机”：手机“下载/DSH”出现文件并收到通知。
2. A 上说“把这段地址复制到我手机”：提示已复制，粘贴到微信内容正确。
3. 手机未武装时：模型工具列表里没有 `phone_*`。
4. 走共享地址武装 30 分钟：Worker 请求增量约 80 次，到期归零。

## 8. P3：手机操控（实验，独立构建版本）

### 8.1 进入条件（闸门，**已拍板**）

三条全部满足才开工：

1. P0 探针证明：澎湃 OS 与 OriginOS 上，侧载的 `bridge` 版能完成“允许受限设置 → 开启无障碍 → 截图 → 点击”，且步骤数可写成图文引导。
2. P1 已发布且有 **≥10 个真实用户**使用（v3 从 20 下调）。
3. 至少 **3 个真实用户**明确提出了操控类场景（不是我们想象的）。

### 8.2 构建版本（置信度：中）

同一份代码出 `bridge` 版本：`applicationId` 与签名和标准版相同，可直接覆盖升级、数据保留；只有 `bridge` 版清单声明 `AccessibilityService`。**【待真机验证】**：国产 ROM 是在安装阶段按清单报警，还是开启无障碍时拦截。

**版本号规则（v3.1 补）**：两个变体必须**共用同一套逐批单调递增的 `versionCode`**，不要给 bridge 单独用更高的号段。否则从 bridge 换回 standard 时，系统会因为“降级”直接拒绝安装；只有卸载重装才会丢应用数据。

**最低版本（v3.1 改）**：如果保留“窗口安全标记（`FLAG_SECURE`）命中就硬拒”这条保证，最低版本必须是 **Android 14（API 34）**——公开接口里没有读取窗口安全标记的方法，`ERROR_TAKE_SCREENSHOT_SECURE_WINDOW` 到 API 34 才存在；API 30–33 只能拿到被遮挡或空白的截图，`withImage=false` 的纯控件树路径更不会触发检查。若坚持 Android 11，就必须删掉这条“绝对保证”，只保留包名、密码框、文字特征三项硬拒。

**截图限频**：`takeScreenshot` 的请求间隔在 AOSP 里 Android 11 是 1000 毫秒、Android 12 起是 333 毫秒，而且不是公开稳定 API。实现要按 **1 秒**建单线程截图队列（500 毫秒只用来等界面稳定），遇到 `ERROR_TAKE_SCREENSHOT_INTERVAL_TIME_SHORT` 延迟重试而不是并发补拍。

### 8.3 工具集（6 个）

| 工具 | 说明 |
|---|---|
| `phone_observe(withImage?)` | 一次调用返回：前台包名、窗口 id、是否锁屏、可交互控件列表（序号、文字、描述、边界框）、`stateToken`；可选附一张本地画好序号框的截图，图片走二进制通道 |
| `phone_open(package)` | 只能打开授权范围内的 App |
| `phone_tap(index 或 {x,y}, stateToken)` | 先点控件；控件失败退回点边界框中心 |
| `phone_input(text, index?, submit?, stateToken)` | 点输入框 → 等焦点 → 填文本 → 可选回车 |
| `phone_swipe(direction, stateToken)` | 上/下/左/右，不让模型算像素 |
| `phone_back()` | 返回键；不提供主页与最近任务 |

所有动作执行完、界面稳定（约 500 毫秒）后自动附带精简 `phone_observe`，把“做一步”与“看一眼”合并成一次往返。

### 8.4 授权模型（置信度：高；触摸检测已移出作废条件）

一次任务授权由手机弹窗确认，弹窗内容全部由手机本地生成，**不显示任何模型可编辑的文字**：

- 哪台电脑（显示名册里的名字）
- 允许操作哪些 App（A 申请包名，手机显示图标与名称）
- 有效时长（默认 10 分钟，最长 30 分钟）

授权期间，以下四个**确定性条件**触发即作废，需重新申请：

- 前台 App 离开授权范围（含回到桌面）
- 屏幕锁定或熄灭（返回错误 `screen_locked`）
- 用户点了通知栏的“停止”
- **5 分钟无任何注入动作**（v3.1 新增的兜底）

**触摸检测不再参与作废判断**（v3.1 定）：`GestureDescription` 只描述本 App 提交的手势，`GestureResultCallback` 只回报该手势完成或被取消，系统不提供“这一下是真人还是注入”的信号，其他触摸只能做启发式。把它当规则，一次误判就让正常滑动丢授权。因此它只作为 P0 的观测指标记录准确率，不进执行逻辑；用户真正急停的入口是通知栏那颗“停止”。

### 8.5 硬拒规则（永不执行，也不弹窗）

以下一律拒绝，只写审计：

- **包名命中**：银行、支付、证券、密码管理器、`com.android.settings`、权限控制器、各家手机管家、安装器、本 App。
- **窗口特征命中**：当前窗口有安全标记（`FLAG_SECURE`），或焦点控件是密码框。**注意**：读安全标记要求 Android 14（见 8.2）；低版本只能靠包名与密码框，这条不能当绝对保证。
- **文字特征命中**：界面出现“支付密码 / 确认付款 / 免密支付 / 转账”等字样。
- **社交发送动作**：微信、QQ、短信、飞书、钉钉里，点“发送”一律拒绝；只能填草稿。

### 8.6 防篡改机制（置信度：高）

| 攻击 | 机制 |
|---|---|
| 本 App 无障碍点掉自己的确认弹窗 | 有确认弹窗等待时，策略引擎**关闭所有注入通道**，A 的动作直接丢弃；确认用系统 `BiometricPrompt`，无障碍无法代按 |
| 中继或中间人伪造指令 | 见下面的“签名信封”与“密钥生命周期”。**签名覆盖整条信封**，不只 `tools/call` |
| 指令在路上时界面已变 | 动作带 `stateToken`；定义见下，接口前当场重算，对不上返回 `409 state_changed` |
| 间接提示注入 | 授权限定 App 范围 + 离开即作废 + 社交 App 禁止点发送 |
| 配对劫持 | 配对码一次性、10 分钟有效；配对成功后两端同时提示“新增了一台手机”；A 的设备列表可随时撤销 |
| 恶意 App 冒充客户端 | 凭据与签名密钥在 Keystore；紧急停止在通知栏（系统界面无法伪造）；只从 GitHub Release 分发并公布证书指纹 |

**签名信封（v3.1 定）**：签名对象是完整信封——`bridgeId`、`keyId`、`msgId`、`seq`、`ts`、方法名、参数摘要、目标 `taskId`。覆盖 A→手机的全部控制消息（`tools/call`、`notifications/cancelled`、任务下发），以及手机→A 的安全敏感回执（工具结果、`state_changed`、拒绝原因）。不做双向验签的话，“中继不可信”这个大前提就不成立，取消指令照样能被伪造成“任务中止”。

**序号与重放（v3.1 定）**：

- 手机按 `bridgeId + keyId` **持久化最高已处理序号**，要求 `seq > lastSeq`（严格大于，相等也拒）；
- 同时按 `msgId` 去重；
- 60 秒时间窗只用于挡时钟漂移和短期缓存，**不是主防线**；
- 手机重启、重装、密钥轮换时开新序号域，并在握手时交换起始序号。

**`stateToken` 定义（v3.1 改）**：不再是“包名 + 窗口 id + 标题摘要”——那三个值在同一窗口里点错按钮时可能不变。改成手机本地生成并保存的**随机 nonce**，绑定：本次观察的界面代次（由无障碍内容事件驱动的单调计数）、前台包名、窗口 id、可交互节点与边界的规范化摘要、过期时间。任何一个动作、界面代次变化或真实触摸都会作废旧 token。

**密钥生命周期（v3.1 新增）**：

- A 在**首次配对前**就生成并持久化 P-256 密钥对与稳定的 `bridgeId`（不是到 P2 才创建，否则 P1 配过的手机没有信任根）；
- 每枚二维码在原有地址与 grant 之外，额外携带同一个 `bridgeId` 与 `keyId = SHA-256(DER SPKI)` 指纹；
- 客户端配对后用设备凭据拉完整公钥、核对指纹，通过才保存；
- 换网络地址不换身份；**换密钥必须重新扫码**（或由旧私钥签名完成轮换）；
- 撤销设备时同步撤销桥凭据与在途任务；换机恢复备份后序号域作废，需要重新配对。

审计：手机本地保存完整记录 7 天（工具名、参数摘要、结果、拒绝原因）；A 端只存脱敏回执（时间、工具名、结果码、拒绝类别），显示在会话轨迹里。截图与输入文字不回传审计。

### 8.7 性能预期（置信度：中）

一步约：截图与控件树 0.3 秒 + 中继上传 0.2～0.6 秒 + 模型推理 1.5～4 秒 + 界面稳定 0.5 秒，**合计 2.5～5.5 秒**。定位：单个 App 内、8 步以内的确定性操作；不承诺长列表搜索与跨 App 串联。

### 8.8 P3 验收

1. A 上说“在备忘录里新建一条‘周三交方案’”：手机弹授权（指纹）→ 完成 → 截图回传，总耗时 < 30 秒。
2. 授权范围是备忘录时，`phone_open("com.tencent.mm")` 被拒绝，审计有记录。
3. 任务中手动切到微信：授权立即作废，A 收到 `scope_left`。
4. 备忘录里写着“打开设置”的界面：模型照做也会被硬拒规则拦下。
5. 伪造签名的 `phone_tap`：被拒绝。
6. 锁屏时调用：返回 `screen_locked`，屏幕不亮。
7. **重放同一条已执行过的指令（相同 `msgId`/`seq`）**：被拒绝；手机重启后再放一遍，仍然拒绝。
8. **陈旧 `stateToken`**：观察后手动改一下界面（例如输入一个字），再用旧 token 点按，返回 `409 state_changed`。
9. **5 分钟无注入动作**：授权自动收回，A 收到 `scope_expired`。
10. **密钥轮换**：A 换钥后用旧指纹发指令，被拒绝；重新扫码配对后恢复。

## 13. 风险

| 风险 | 概率 | 对策 |
|---|---|---|
| 国产 ROM 后台杀连接，通知迟到或丢失 | 高 | 只承诺任务期间保活；空闲走 ntfy；设置页如实写“空闲时提醒可能延迟” |
| 团队被 ROM 兼容问题拖住，主插件停摆 | 高 | 只适配 P0 那 3 台机器；不写单一 ROM 的保活技巧；每周给客户端设工时上限 |
| 原生客户端改变审批归属，电脑一直卡住 | 中 | 双状态方案默认关，网页行为不变，纳入回归测试 |
| 手机桥长轮询耗尽共享中继配额 | 中 | 武装制 + 共享地址每日 2 小时硬上限 + 全局日预算 + 运维监控 |
| 配额口径误判导致阈值设错 | 中 | 先核实“原始额度”和“代理请求上限”各自的口径，再调阈值 |
| **配对链路断点**（v3.1 新增） | 中 | 原生配对接口是 P1 的第一件事，没它就扫码只能拿到临时令牌 |
| P3 演示好、实际不行 | 高 | 闸门要求真实场景；对外定位“实验”，承诺限定单 App 8 步内 |

## 14. 已拍板的问题（2026-11-04）

| # | 问题 | 结论 | 理由 |
|---|---|---|---|
| 1 | 「审批优先发到手机」默认值 | **默认关；打开后手机等待 120 秒** | 保持网页行为不变是最好的兼容；120 秒够人看见并处理，又不至于让电脑干等 |
| 2 | P3 闸门的用户数 N | **10（原 20 下调），3 个真实场景保留** | 门槛要卡“有没有真需求”，不是凑人数 |
| 3 | 社交 App 禁止点“发送” | **接受，只能写草稿** | 代点发送一旦出错，损失的是用户在朋友/同事那里的信誉 |
| 4 | 共享固定地址是否禁止手机桥 | **不禁止；提示 + 每日 2 小时硬上限 + 全局预算** | 一刀切会挡住没有 Tailscale 的用户；限时既保住公共配额，也留了可用性 |
| 5 | B 端长轮询是否纳入武装制 | **不纳入，只加监控** | B 端是既有产品体验；手机桥是新东西，可以要求 |
| 6 | `FLAG_SECURE` 硬拒与最低版本（v3.1 新增） | **两条路二选一**：要这条绝对保证，就把 bridge 最低版本提到 Android 14；坚持 Android 11 就删掉这条保证 | 公开接口读不到窗口安全标记，API 30–33 做不到 |
| 7 | 剪贴板写入是否每次确认（v3.1 新增） | **每次确认** | 单次注入就能替换收款地址或命令，频率限制挡不住 |
| 8 | 触摸检测是否参与收回授权（v3.1 新增） | **不参与，只做观测指标** | 系统不提供“真人还是注入”的信号，误判代价是用户正常使用被打断 |

仍然需要真机才能定的事：P0-a 的权限步骤数与过夜存活、P0-b 的唤醒延迟、触摸启发式的准确率、`bridge` 版在不同 ROM 上的安装拦截位置。
